# 클라우드 비용과 자원 효율의 기초

> 클라우드에서 비용, 할당 자원, 실제 사용량, 성능, 낭비는 어떤 관계가 있으며 서로 어떻게 다른가?

이 문서는 AWS 서비스별 비용을 살펴보기 전에 필요한 구분을 정리한 첫 학습 자료다. 아래 개념 설명과 판단 예시는 공식 자료를 바탕으로 한 이 문서의 해석이며, 실제 계정의 청구·성능을 검증한 결과가 아니다.

## 1. 비용: 무엇에 단가를 곱하는가

클라우드 사용료는 보통 **과금 대상 사용량 × 해당 단가**를 항목별로 계산해 합산한다. 사용량은 인스턴스 실행 시간, 할당한 스토리지 용량과 기간, 전송한 데이터량처럼 항목마다 다르다. 단가는 그 사용량 한 단위의 가격이고, 과금 단위는 시간·초·GB-월 등 계산의 기준이다. 따라서 CPU 사용률 20%는 관측값이지 곧바로 인스턴스 요금의 20%라는 뜻이 아니다. EC2 On-Demand 가격 안내는 컴퓨팅 용량의 시간 또는 초 단위 과금을 설명하며, EBS 가격 안내의 예시는 볼륨 유형에 따라 할당 용량·기간, 별도 프로비저닝한 IOPS 등이 과금에 관여함을 보여 준다. [AWS EC2 가격](https://aws.amazon.com/ec2/pricing/on-demand/), [AWS EBS 가격](https://aws.amazon.com/ebs/pricing/)

여기서 계산한 **사용료**와 청구서의 **실제 결제액**도 구분해야 한다. 할인 약정·할인 적용 방식, 크레딧, 세금, 다른 서비스의 사용료 등에 따라 결제액은 단순한 정가 사용료 합계와 달라질 수 있다. 비용을 비교할 때는 기간과 시간대, 리전, 운영체제, 요금 방식과 할인·크레딧·세금의 포함 여부를 함께 적는다. 비교 기준이 다르면 비용 차이를 자원 구성의 효과로 돌릴 수 없다.

## 2. 할당 자원과 실제 사용량

**할당 자원(Provisioned/Allocated Resources)**은 사용할 수 있도록 마련한 용량이다. 예를 들어 인스턴스의 vCPU·메모리나 EBS 볼륨의 할당 용량이 있다. **실제 사용량(Utilization)**은 그 자원을 관측 기간에 얼마나 썼는지를 나타낸다. CPU 사용률, 메모리 점유, 디스크 사용 공간과 I/O는 서로 다른 관측값이다. 스토리지의 사용 공간이 적어도 할당 용량에 대한 요금이 생길 수 있고, CPU 사용률이 낮아도 실행 중인 인스턴스의 기본 요금은 그 비율로 자동 축소되지 않는다. 반대로 어떤 서비스는 요청량이나 데이터 처리량이 직접 과금량에 가깝다. 먼저 해당 항목의 과금 기준을 확인해야 한다.

평균은 기간 전체의 수준을 보여 주지만 짧은 과부하를 가릴 수 있다. 피크는 최대 관측값이지만 측정 간격과 일시적 급증에 민감하다. p95는 관측값의 약 95%가 그 값 이하라는 뜻이며, 남은 5%의 악화와 지속 시간은 별도로 봐야 한다. 세 수치를 비교할 때는 같은 기간·집계 간격·측정 대상을 써야 한다. 특히 평균 CPU만 보고 작은 인스턴스로 바꾸면 피크 시간의 응답 지연을 놓칠 수 있다.

## 3. 비용과 성능·품질을 함께 보기

**응답시간(Latency)**은 요청에 응답하는 데 걸린 시간, **처리량(Throughput)**은 단위 시간에 처리한 요청이나 작업 수, **오류율(Error Rate)**은 요청 중 실패한 비율이다. 비용이 낮은 구성이더라도 필요한 응답시간, 처리량, 오류율과 안정성 요구를 충족하지 못하면 같은 서비스를 제공한다고 보기 어렵다. AWS Well-Architected의 비용 최적화 소개도 기능 요구를 충족하면서 자원을 효과적으로 쓰는 관점을 제시한다. [AWS Cost Optimization Pillar](https://docs.aws.amazon.com/wellarchitected/latest/cost-optimization-pillar/welcome.html)

비교 단위를 서비스의 성과에 맞추면 **단위경제(Unit Economics)**를 볼 수 있다. 예를 들어 요청당 비용은 같은 기간의 관련 비용을 성공적으로 처리한 요청 수로 나눈 값이고, 작업당 비용은 완료 작업 수로 나눈 값이다. 분모의 정의와 포함 비용 범위를 고정해야 의미가 있다. 트래픽이 늘어 총비용이 올라도 요청당 비용은 내려갈 수 있다. FinOps Framework는 사용량·비용 이해와 단위경제를 별도 활동 영역으로 제시한다. [FinOps Framework](https://www.finops.org/framework/)

## 4. 낭비, 이상, 저활용, 과다 할당

| 개념 | 여기서 쓰는 뜻 | 바로 결론 내릴 수 없는 이유 |
|---|---|---|
| 낭비(Waste) | 필요한 서비스 품질이나 목적에 기여하지 않으면서 피할 수 있는 지출 | 필요한 여유 용량이나 복구 대비일 수 있음 |
| 이상(Anomaly) | 기대한 비용·사용 패턴에서 벗어난 변화 | 정상적인 수요 증가나 배포 변화일 수 있음 |
| 저활용(Underutilization) | 할당 자원에 비해 관측 사용량이 낮은 상태 | 피크·장애 대응·미관측 사용량을 확인해야 함 |
| 과다 할당(Overprovisioning) | 필요한 수준보다 많은 자원을 마련한 상태 | 실제 필요량과 품질 요구를 먼저 정해야 함 |

높은 비용은 수요가 늘거나 성능·안정성을 위해 필요한 자원을 쓴 결과일 수 있다. 낮은 평균 사용률도 피크를 버티기 위한 용량이라면 곧바로 낭비가 아니다. 반면 사용되지 않는 자원이 계속 과금되고 업무·복구 목적도 확인되지 않는다면 낭비 후보가 된다. 비용 이상은 조사 시작 신호이지 낭비 판정 자체가 아니다. 이 구분은 이 문서의 판단 틀이며, 개별 환경에서의 판정은 추가 근거가 필요하다.

## 5. 판단에 필요한 근거

낭비를 주장하려면 인프라 구성과 설정(크기·실행 상태·스토리지 연결 등), 실제 자원 사용량, 비용 데이터의 과금 항목, 업무량과 시간별 패턴, 응답시간·오류율·복구 목표 같은 성능·안정성 요구를 같은 기간에 맞춰 본다. 예를 들어 낮은 CPU 평균만 있고 메모리 사용량이나 피크 트래픽이 없다면 축소 가능성을 확정할 수 없다. 비용 항목의 귀속이 불분명하거나 측정 기간이 어긋나도 판단을 보류하고 누락 자료를 기록한다.

## 6. 가상 계산 예제

**가정:** 한 EC2 On-Demand 인스턴스의 *가상* 기본 단가가 시간당 0.10 USD이고, 동일한 인스턴스를 100시간 실행한다. 시간 단위로 정확히 과금되는 단순한 조건을 가정한다. 할인, 크레딧, 세금, EBS, 데이터 전송, 공인 IP 등 부가 비용은 모두 제외한다. 이 값은 실제 AWS 가격이 아니다.

인스턴스 사용료는 **0.10 USD/시간 × 100시간 = 10.00 USD**다. 이 기간의 평균 CPU 사용률이 40%에서 10%로 달라져도 인스턴스와 실행 시간이 그대로라면 위 기본 사용료는 **10.00 USD**다. CPU가 덜 바빴다는 사실만으로 요금이 4분의 1이 되지는 않는다. 구성이나 실행 시간을 바꿀 여지가 있는지는 피크 사용량과 성능 요구를 확인한 뒤 판단해야 한다. 실제 가격으로 계산할 때는 리전·운영체제·인스턴스 유형·가격 조건·확인일을 기록하고, 다른 과금 항목을 별도로 합산한다.

- **이번 문서에서 설명할 수 있는 내용:** 사용량·단가·과금 단위와 관측 사용률의 차이, 비용을 서비스 품질과 함께 비교해야 하는 이유, 낭비와 비용 이상의 구분.
- **일반 원리이며 실제 환경 확인이 필요한 내용:** 어떤 구성이 과다 할당인지, 어느 비용이 실제 낭비인지, 구성 변경 후 요청당 비용과 품질이 어떻게 변하는지.
