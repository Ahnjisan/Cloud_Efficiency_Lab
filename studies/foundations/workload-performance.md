# 워크로드 성능 — 지연·처리량과 JVM

자원 설정을 비교할 때 같은 업무량을 같은 품질로 처리했는지 먼저 묻는다. [Linux 자원](linux-resources.md)의 CPU·메모리 계측과 [Docker 자원 제한](../platforms/docker/resource-constraints.md)을 연결한다.

## 부하와 서비스 품질

CPU-bound 단계는 실행 시간 대부분을 연산에, I/O-bound 단계는 디스크·네트워크 응답 대기에 쓴다. 한 서비스에서도 단계별 성격이 다르다. 동시성은 동시에 진행 중인 작업 수다. 대기 위주 작업은 동시성 증가로 처리량이 좋아질 수 있지만 포화 뒤에는 대기열과 오류만 늘 수 있다. 입력 건수/s와 성공 처리량, 오류율, 지연 분포를 함께 기록한다. p95·p99는 각각 하위 95%·99% 요청이 들어오는 지연 경계이며, 인스턴스별 p99 평균은 전체 요청의 p99를 재현하지 못한다.

JVM 메모리에는 관리 힙 외에도 스레드 스택, 클래스 메타데이터, 직접 버퍼 등 네이티브 사용분이 있다. GC의 빈도·중단·CPU 부담은 할당률과 살아 있는 객체, 컬렉터 설정에 따라 달라진다. 힙 최대값과 프로세스 RSS 또는 컨테이너 제한을 대조한다.

비교할 워크로드는 입력 크기·요청 유형 비율·도착 패턴·동시성으로 명시한다. 포화 여부는 처리량이 평평해지면서 대기열이 증가하는지, 제약 자원의 대기 또는 스로틀링이 동반되는지로 좁힌다.

## 가상 비교

동일한 1,000건을 보낸 A는 p99 180 ms·오류 5건, B는 p99 260 ms·오류 20건이다. p99 200 ms 이하와 오류율 1% 이하가 기준이라면 A(0.5%)만 통과한다. 지연을 성공 요청만으로 계산했으면 실패 요청 수와 분모를 별도로 표시한다. GC 로그, JFR, 애플리케이션 히스토그램과 CPU·I/O 압력을 같은 시간축에서 대조한다. 입력 분포, 워밍업, 캐시, 버전이 다른 두 측정만으로 구성 효과를 결론 내리기 어렵다.
