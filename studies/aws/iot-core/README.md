# IoT Core 비용 산정 01 — 메시지 계량·연결 시간·Rules Engine

[AWS 서비스 목차](../README.md)

> 센서가 같은 양의 데이터를 보내더라도, 메시지를 하나씩 보낼 때와 여러 건을 묶어 보낼 때 비용과 지연은 어떻게 달라지는가?

커리큘럼 02. AWS Infrastructure & Pricing의 학습 노트입니다. 실제 프로젝트에서 운영할 IoT 센서 파이프라인(센서 → AWS IoT Core → Kinesis Data Firehose → S3 → Glue/Athena)의 첫 단계를 다룹니다. 요율은 **AWS Price List의 서울 리전(ap-northeast-2) 공개 On-Demand 요율**이며, 작업량은 가상 값입니다.

## 1. 과금 단위

| 항목 | 계량 방식 | 서울 리전 요율 |
|---|---|---|
| 메시지(Messaging) | 디바이스↔IoT Core 사이 MQTT·HTTP 메시지. **5 KB 단위로 계량**합니다. 8 KB 메시지는 2건으로 계산됩니다. 최대 메시지 크기는 128 KB입니다. | 월 첫 10억 건까지 **1.20 USD/100만 건**, 다음 40억 건 0.96 USD, 50억 건 초과 0.84 USD |
| 연결 시간(Connectivity) | 디바이스가 연결된 시간을 **1분 단위**로 계량합니다. | **0.096 USD/100만 분** |
| 규칙 실행(Rules triggered) | 규칙이 평가될 때마다 계산하며 **메시지 크기 5 KB 단위**로 계량합니다. | **0.18 USD/100만 건** |
| 액션 실행(Actions executed) | 실행된 액션마다 계산하고 5 KB 단위로 계량합니다. **규칙당 최소 1개 액션**으로 계산합니다. | **0.18 USD/100만 건** |
| Device Shadow·Registry | 섀도·레지스트리 조작 건수 | 1.50 USD/100만 건 |

- **Basic Ingest**: 예약 토픽(`$aws/rules/<규칙 이름>`)으로 보내면 메시지 요금이 붙지 않고 규칙·액션 요금만 적용됩니다. Basic Ingest는 발행·구독 브로커를 경로에서 빼므로 디바이스와 규칙이 이 예약 토픽을 구독할 수 없습니다. 따라서 "센서 → 규칙 → Firehose" 단방향 경로에 맞는지 먼저 확인합니다.
- **무료 제공량**: 계정 생성 후 12개월 동안 월 연결 225만 분, 메시지 50만 건, 섀도·레지스트리 22.5만 건, 규칙 25만 건·액션 25만 건이 제공됩니다. 이 문서의 계산에서는 제외합니다.
- **"5 KB"의 바이트 정의**: 요금 페이지는 5 KB라고만 적고 5,000 B인지 5,120 B인지 밝히지 않습니다. 묶음 크기를 경계 근처로 정할 때는 실제 계정의 계량(CUR 사용량)으로 확인해야 합니다. 이 저장소의 실험은 두 값을 모두 계산합니다.

## 2. 가상 예제 — 개별 전송과 20건 묶음

센서 100대가 10초마다 200 B 측정값 1건을 만들고, 30일(43,200분) 동안 항상 연결돼 있다고 가정합니다. 규칙 1개가 액션 1개(Firehose)를 실행합니다.

| 구성 | 월 계량 메시지 | 메시지 요금 | 규칙+액션 | 연결 | 합계 | 추가되는 최대 대기 |
|---|---:|---:|---:|---:|---:|---:|
| 개별 전송 (200 B × 1) | 25,920,000 | 31.10 USD | 9.33 USD | 0.41 USD | **40.85 USD** | 0초 |
| 20건 묶음 (약 4,000 B × 1) | 1,296,000 | 1.56 USD | 0.47 USD | 0.41 USD | **2.43 USD** | 190초 |

- 계산: `100대 × 6건/분 × 43,200분 = 25,920,000건`, `25.92 × 1.20 = 31.10 USD`. 묶음 1건이 5 KB를 넘지 않아 계량 메시지 수가 1/20로 줄어듭니다.
- 연결 요금은 묶음과 무관합니다. `100 × 43,200 ÷ 1,000,000 × 0.096 = 0.41 USD`.
- 묶음의 대가는 **지연**입니다. 첫 측정값은 나머지 19건이 모일 때까지 `19 × 10초 = 190초` 기다립니다. 묶음 크기가 5 KB 경계를 넘으면(예: 26건 × 200 B = 5,200 B) 다시 2건으로 계량되어 절감 폭이 꺾입니다.

이 예제의 비율(약 94% 감소)은 페이로드가 5 KB보다 훨씬 작을 때만 성립합니다. 페이로드가 이미 수 KB라면 묶음 효과는 작습니다. 연결 요금, 디바이스 메모리·배터리, 장애 시 잃는 데이터 양은 같은 표에 넣어 비교합니다.

## 3. 낭비가 생기는 조건과 판단 근거

1. **작은 메시지를 자주 보냄**: 메시지당 5 KB를 채우지 못한 만큼 낭비됩니다. 판단에는 디바이스별 평균 페이로드 크기와 전송 주기가 필요합니다. CloudWatch의 IoT 지표만으로는 크기 분포를 알기 어려우므로 디바이스 측 로그나 규칙 SQL로 크기를 기록합니다.
2. **불필요한 규칙 평가**: 같은 토픽에 규칙이 여러 개 걸리면 메시지 1건이 규칙 수만큼 계량됩니다. 규칙 수와 토픽 매핑을 확인합니다.
3. **신선도 요구가 낮은데 실시간으로 보냄**: 데이터가 몇 분 뒤에야 조회돼도 되는 분석용 경로라면 묶음 전송의 지연은 품질 저하가 아닙니다. 반대로 경보·제어 경로는 묶음 대상이 아닙니다. **어떤 토픽이 어떤 신선도 요구를 갖는지 모르면 판단을 보류**합니다.

## 확인 문제 정답과 해설

1. 6 KB는 5 KB 단위 두 개가 필요하므로 2건입니다.
2. 5,000 B를 5 KB로 보면 정확히 1건이고, 5,120 B로 보면 역시 1건입니다. 다만 JSON 배열 기호·필드 이름 같은 오버헤드가 붙으면 5,000 B 기준에서는 2건이 될 수 있어 경계 바로 아래로 묶음 크기를 정하는 것은 위험합니다.
3. 메시지 요금이 사라집니다. 규칙 실행·액션 실행·연결 요금은 그대로 남습니다.
