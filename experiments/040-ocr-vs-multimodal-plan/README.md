# 040 — Textract + Bedrock vs Bedrock 이미지 직접 입력

[실험 목차](../README.md) · [037 장당 구조화 비용](../037-measurement-sheet-unit-cost/README.md) · [025 실제 과금 확인 실험의 승인·정리 절차](../025-billing-rule-probe/README.md)

**실행 완료(2026-11-27), 채점 재현 PASS.** Haiku 4.5: H1 기각, H2·H3 지지. Sonnet 4.6: H1 지지, H2·H3 기각. 저장소 소유자가 실행을 지시했다("측정지·손글씨도 만들어서 직접 해줘"). "실행 전 결정(확정)"과 채점기는 실행 전에 썼고, 실행 뒤 가설·채점 규칙을 바꾸지 않았다. **손글씨는 컴퓨터로 만든 글꼴 기반 합성이라 실제 사람 손글씨 결론이 아니다.** 실제 청구 확인은 반영 뒤 할 예정이다.

## 질문

손글씨 측정지에서 측정값을 공통 형식으로 옮길 때, 세 가지 방식의 **숫자 정확도**와 **장당 비용**은 어떻게 다른가?

| 안 | 흐름 |
|---|---|
| P1 | Textract AnalyzeDocument(Tables) → 추출 텍스트·표를 Bedrock(텍스트)으로 구조화 |
| P2 | Bedrock 멀티모달에 측정지 이미지를 직접 넣어 구조화 (OCR 없음) |
| P3 | P1의 Textract 결과와 이미지를 함께 Bedrock에 넣어 구조화 |

[037](../037-measurement-sheet-unit-cost/README.md)에서 장당 비용은 Textract 종류가 가장 크게 바꿨다(기준 구성에서 Textract 69%). Textract를 빼는 P2가 정확도를 지키면 비용 구조가 바뀐다. 그 정확도는 계산으로 알 수 없어 실제 호출이 필요하다.

## 실행 전 결정 (확정, 2026-11-27 실행 전)

| 항목 | 내용 |
|---|---|
| 가설 H1 | P2(이미지 직접)의 손글씨 숫자 필드 정확도는 P1(Textract → 텍스트)보다 낮지 않다(차이 −1%p 이내). 모델마다 판정 |
| 가설 H2 | P2의 장당 비용은 P1의 50% 이하다(같은 모델, 응답 사용량 기준) |
| 가설 H3 | P3(이미지 + Textract)는 소수점·부호 오독률이 세 안 중 가장 낮다(모델마다 판정) |
| 1차 지표 | 손글씨 숫자 필드 정확도 = 정답과 수치가 같은 필드 ÷ 손글씨 필드 수(805개). 끝자리 0 생략(42.50 → 42.5)은 수치가 같으므로 정답, 엄격 지표(문자열 일치)는 따로 기록 |
| 오류 분류 | 누락(항목·필드 없음, 숫자로 읽을 수 없음), 부호 오류(절댓값은 같고 부호가 다름), 소수점 오류(숫자 배열은 같고 소수점 위치·자릿수가 다름), 그 밖의 오독 |
| 1% 목표 | 손글씨 오독 1% 이하를 예비 판정 기준으로 쓴다. 오류율의 95% 윌슨 신뢰구간을 함께 적고, 상한이 1%를 넘으면 "목표 충족 미확인"으로 둔다 |
| 항목 매칭 | 정답의 측정 항목 이름과 응답의 spec_item을 공백 제거 후 비교, 같지 않으면 유사도 0.6 이상 중 가장 비슷한 항목. 측정값이 여러 개(양식 B)면 순서대로 |
| 모델·프로필 | Claude Haiku 4.5, Claude Sonnet 4.5, Global 교차 리전 추론 프로필(합성 자료라 처리 위치 위험 낮음, 요율 확인됨). 서울에서 쓸 수 있는 프로필 ID는 실행 직전 `list-inference-profiles`로 확인 |
| 호출 | Bedrock Converse, 온도 0, 최대 출력 3,000토큰, 시스템 프롬프트·출력 JSON 스키마 고정([run_040.py](run_040.py)). Textract AnalyzeDocument(TABLES)는 장마다 1회만 호출하고 결과를 P1·P3와 모든 반복에서 재사용(결정적 서비스) |
| 반복·순서 | 장 순서를 시드 40으로 섞고, Haiku 3회 → Sonnet 3회 순서. 장마다 세 안의 순서를 돌려 가며 바꾼다 |
| 비용·중단 | 누적 예상 비용(응답 usage × 요율 + Textract) 10 USD에서 중단, 같은 오류 연속 2회, 스로틀링 재시도 3회 초과, 실행 시간 110분 초과 시 중단. 예산 상한 15 USD |
| 데이터 | 합성. 아래 "설계 변경 기록" 참조. 이미지·정답표·응답 원문은 저장소 밖(`Documents/cloud-efficiency-raw/040/`) |

## 설계 변경 기록

- **2026-11-27, 실행 전 — 손글씨를 사람이 아니라 컴퓨터로 생성**: 저장소 소유자 지시에 따라 팀원 손글씨 대신 [make_sheets.py](make_sheets.py)로 30장을 만들었다. Windows 손글씨풍 글꼴 3종(Ink Free, Segoe Print, Segoe Script)을 "필기자" 3명으로 쓰고, 글자마다 기울기·높이·크기·간격·잉크 색을 흔들었다. 양식 3종(A: 모든 값 손글씨, B: 규격 인쇄 + 측정값 3회 손글씨, C: 도면 치수·공차·실측·편차 손글씨) × 10장, 30장 중 6장에 흐린 칸과 줄 그어 고친 값을 넣었다. 손글씨 필드 805개(음수 158개), 인쇄 필드 177개. **실제 사람 손글씨보다 글자 모양이 고르므로, 이 결과로 "손글씨 오독 1% 이하"를 판단할 수 없다.** 실제 손글씨 판정은 사람이 쓴 측정지로 다시 해야 한다.
- **2026-11-27, 실행 전 — S3·IAM 자원 없음**: Textract와 Bedrock 모두 이미지 바이트를 직접 받으므로 S3 버킷과 IAM 역할을 만들지 않는다. CloudShell 홈에 올린 파일만 정리 대상이다.
- **2026-11-27, 실행 중 — Sonnet 4.5 대신 Sonnet 4.6**: Haiku 4.5 270회를 마친 뒤 Sonnet 4.5 첫 호출 2회가 `ResourceNotFoundException`("공급자가 Legacy로 지정했고 최근 30일 동안 이 계정이 쓰지 않음")으로 거부돼 실행기가 중단 규칙대로 멈췄다. 같은 계열의 활성 모델 중 Sonnet 5.5와 Sonnet 5는 `AccessDeniedException`("이 계정에서 사용할 수 없음")이었고, Sonnet 4.6은 1회 시험 호출(입력 10·출력 4토큰)에 응답했다. Sonnet 4.6의 서울 Global 요율이 Sonnet 4.5와 같아(입력 3.00·출력 15.00 USD/100만 토큰, [Price List 서울 오퍼](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrockFoundationModels/current/ap-northeast-2/index.json) 게시일 2026-11-23) 비용 비교의 뜻이 유지되므로 **Sonnet 4.6으로 바꿔** 이어서 실행했다. 가설·채점 규칙은 바꾸지 않았다. 결과의 "Sonnet"은 Sonnet 4.6이다. 거부된 호출은 과금되지 않는 것으로 보고 비용에 넣지 않았고, 접근 시험 호출 2회(Sonnet 4.6 응답 1회, Sonnet 5 거부 1회, 합계 1센트 미만)도 넣지 않았다.
- **2026-11-27, 실행 전 — Textract 1회 재사용**: 계획은 P1·P3 반복마다 Textract를 부르는 것이었지만, Textract는 같은 입력에 같은 결과를 주므로 장마다 1회만 부르고 재사용한다(예상 비용 2.70 → 0.45 USD).

## 합성 측정지 30장 준비 (계획 당시 — 실제로는 "설계 변경 기록"대로 컴퓨터로 생성)

- 팀원이 **손으로 직접 쓴 가상 측정지** 30장. 실제 고객·회사·도면 자료를 쓰지 않는다. 회사명·고객사명 칸은 비우거나 "가상"으로 쓴다.
- 양식 3종 × 10장(표 칸 크기·항목 순서가 다른 가상 양식). 장마다 측정값 15~25개, 공차(±, +/−0.0x), 소수점 0~3자리, 음수 일부 포함.
- 필기자 3명 이상(글씨체 다양성), 펜 2종, 일부러 흐린 칸·겹친 숫자·지운 흔적을 30장 중 6장에 넣는다.
- 촬영: 스마트폰 2종, 조명 2조건, 정면/약간 기울임. 장당 이미지 1개(JPEG, 긴 변 2,000 px 이하로 고정).
- **정답표**: 쓰기 전에 값을 먼저 정하고(스프레드시트), 쓴 뒤 2명이 대조 확인. 정답표는 이미지와 같은 ID로 연결한다.
- 이미지와 정답표는 저장소 밖에 둔다(저장소에는 생성 절차와 집계 결과만).

## 위험

- 오독 1%를 30장으로 확정할 수 없다(표본 부족) → 예비 판정으로만 쓰고, 합격선 근처면 표본을 늘리는 2단계 계획을 따로 승인받는다.
- Global 프로필은 요청이 국외 리전에서 처리될 수 있다. 합성 자료라 위험은 낮지만, 실제 운영 결론으로 옮길 때는 처리 위치 조건을 맞춰 다시 측정해야 한다.
- 모델 응답 변동으로 정확도가 실행마다 달라질 수 있다(3회 반복으로 범위 기록).
- 청구 반영이 하루 이상 늦어 실제 비용 확인이 늦다([025](../025-billing-rule-probe/README.md)에서 24시간 시점 미반영).

## 유지 시간·중단 조건·정리

- **유지 시간**: 실행 2시간 이내. S3 임시 버킷은 실행 당일 삭제.
- **중단 조건**: (1) 누적 예상 비용이 10 USD 도달, (2) 같은 오류 2회, (3) 스로틀링으로 재시도가 장당 3회 초과, (4) 예상하지 못한 자원 생성 발견 → 즉시 멈추고 기록.
- **정리**: S3 객체·버킷 삭제, IAM 임시 역할·정책 삭제, CloudShell 임시 파일 삭제, 남은 자원 0건 확인 후 기록(025와 같은 절차). Textract·Bedrock은 남는 자원이 없다.

**오류 내용**

- **P1의 "누락" 81건은 사실상 소수점 오류다.** Textract가 소수점을 쉼표로 읽은 값(`18.000` → `18,000`)을 모델이 그대로 옮겼다(3회 합 72건). 미리 정한 규칙상 숫자로 읽을 수 없는 값은 누락으로 분류했다. Textract는 소수점을 빼거나(`42.748` → `42748`) 쉼표로 읽는 경우가 있었고, 한글 인쇄 항목명은 잘 읽었다.
- **Haiku P2의 "누락" 228건은 대부분 한글 항목명 오독이다.** 숫자는 맞게 읽었지만 인쇄된 항목명을 `깊이` → `길이`·`김이`, `단차` → `단자`처럼 잘못 읽어 정답 항목과 짝을 찾지 못했다(225필드). 사후 분석으로 짝을 못 찾으면 같은 행 순서의 항목을 쓰면 Haiku P2 정확도는 **96.77%**(오류율 2.6~4.0%)다. 이 사후 분석은 가설 판정에 쓰지 않았다.
- **Sonnet 4.6의 오류는 모두 소수점 누락이다**(`25.0` → `250`, `30.273` → `30273`). 항목명 오독·부호 오류는 0건이었다.
- **부호 오류는 모든 조건에서 0건**이었다(음수 필드 158개).
- **흐린 칸·고친 값**(9필드 × 3회): Sonnet P2·P3 27/27, Haiku P3 21/27, Haiku P2 18/27, Sonnet P1 12/27, Haiku P1 9/27. Textract를 거치면 흐린 값과 줄 그은 값을 잘 처리하지 못했다.

**가설 판정**

| 가설 | Haiku 4.5 | Sonnet 4.6 |
|---|---|---|
| H1 P2 정확도가 P1보다 1%p 넘게 낮지 않다 | **기각** (87.83% 대 95.40%) | **지지** (98.76% 대 95.65%) |
| H2 P2 장당 비용 ≤ P1의 50% | **지지** (0.0048 대 0.0189, 26%) | **기각** (0.0135 대 0.0245, 55%) |
| H3 P3의 소수점·부호 오류가 가장 적다 | **지지** (15 대 18·42) | **기각** (27 대 P1 18·P2 30) — P1은 소수점 오류가 "누락"(쉼표)으로 분류돼 수가 적게 보인다 |

**1% 목표 대비**: 가장 좋은 Sonnet 4.6 P3도 오류율 1.12%(신뢰구간 0.77~1.62%)로 **목표 충족 미확인**이다. 게다가 이 결과는 합성 글꼴 손글씨라 실제 손글씨 판정 근거가 아니다.

## 해석

- **Textract를 앞에 두는 것(P1)이 정확도를 보장하지 않았다.** Textract의 소수점 → 쉼표 오독이 그대로 전달돼 두 모델 모두 P1이 95% 수준에 머물렀다. 이미지를 함께 주면(P3) 모델이 이를 고쳤다(Haiku 95.4 → 97.6%, Sonnet 95.7 → 98.9%).
- **모델 성능이 충분하면 Textract를 뺄 수 있다.** Sonnet 4.6 P2는 P1보다 정확하고(98.8% 대 95.7%) 장당 45% 싸다(0.0135 대 0.0245). Haiku 4.5는 이미지 단독(P2)에서 한글 항목명을 잘못 읽어 그대로는 쓰기 어렵다.
- **비용과 정확도의 선택지**: Haiku P2(0.0048, 87.8%, 항목명 오독 문제) → Haiku P3(0.0205, 97.6%) → Sonnet P2(0.0135, 98.8%) → Sonnet P3(0.0307, 98.9%). 이 합성 조건에서는 **Sonnet 4.6 P2가 Haiku P3보다 싸고 정확했다.** [037](../037-measurement-sheet-unit-cost/README.md)의 "Textract가 장당 비용의 69%"와 함께 보면, 장당 비용의 가장 큰 항목을 없애는 선택지가 정확도도 높았다.
- 남은 오류는 거의 전부 **소수점 누락**이다. 운영 규칙(예: 같은 항목의 기준값·공차와 자릿수 대조, 기준값의 10배·0.1배 차이 경고)으로 잡을 수 있는 유형이다.
- InfraFit 후보 C-OCR-1의 근거를 보강한다: "Textract → LLM 텍스트" 구성이 이미지 직접 입력보다 비싸고 덜 정확한 조건이 있다(후보, 실제 손글씨 확인 필요).

## 가정·제외·한계

- **합성 손글씨**: Windows 손글씨풍 글꼴 3종을 흔든 이미지다. 실제 사람 손글씨는 글자 모양이 훨씬 다양해 정확도가 더 낮을 수 있다. 특히 소수점 크기·위치는 글꼴과 흐림 효과에 따라 정해졌다.
- 모델 응답만으로 비용을 계산했다(usage × Price List 요율). 실제 청구액은 반영 뒤 Cost Explorer로 확인할 예정이다(최대 4건).
- Sonnet은 계획의 4.5가 아니라 4.6이다(요율 같음). Global 교차 리전 프로필이라 요청이 국외 리전에서 처리됐을 수 있다(합성 자료).
- 30장·3양식·필기자 3종의 작은 표본이다. 같은 이미지를 3회 반복해 모델 변동은 없었지만, 이미지 쪽 변동(촬영 조건)은 다루지 않았다.
- 항목 매칭은 미리 정한 규칙(이름 일치 또는 유사도 0.6)이다. 짧은 한글 항목명(두 글자)은 한 글자만 틀려도 유사도 0.5라 짝을 못 찾는다. 이 영향은 사후 분석으로 따로 보였다.
