# 023 — 실제 계정의 일별 비용으로 R-COST-1 점검

[실험 목차](../README.md) · [수집·재설정 계획](../real-account-calibration-plan.md) · [021 합성 평가](../021-daily-cost-spike-detection/README.md) · [InfraFit 운영 규칙](../../infrafit/README.md#운영-규칙-r-fh-2-r-ath-12-r-sm-1-r-cost-1)

**실제 계정 데이터 점검 완료. 세 질문 모두 "예", 기준값은 조정하지 않고 보류로 기록.** 아래 "실행 전 결정"은 데이터를 보기 전에 작성했고 결과를 본 뒤 바꾸지 않았다. 실제 비용은 Cost Explorer 요청 1건, 0.01 USD다.

> **024 이후 갱신.** 이 실험이 찾은 문제를 [024](../024-cost-spike-rule-fixes/README.md)에서 고쳤고, InfraFit 기본 규칙이 바뀌었다. `check.py`는 기본으로 024 이전 규칙에 고정해 이 실험의 결과를 재현한다(`--current-rule`을 주면 현재 기본값). 대기열 금액 표시를 소수 넷째 자리로 고친 뒤 다시 만든 [result.json](result.json)에서는 경보 수와 위치는 같고, 2월 경보의 관측값 ÷ 기준 비율이 1.0에서 **1.11**로 바로잡혔다(소수 둘째 자리 반올림에 가려져 있던 +10.7%).

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 1 | 현재 기준값(28일 중앙값 + 3 × 1.4826 × MAD, 10% 하한, 경보일 유지)의 R-COST-1이 실제 계정의 일별 비용에서 경보를 내는가? |
| 질문 2 | 경보가 난다면 월 경계, 세금, `Estimated` 날짜처럼 합성 실험(021)에서 만들지 않은 실제 청구 패턴과 관련이 있는가? |
| 질문 3 | 비용이 거의 일정한 서비스(MAD가 0에 가까움)에서 10% 하한이 실제로 경보를 막는 역할을 하는가? |
| 데이터 | 실제 계정. Cost Explorer `GetCostAndUsage`, `Granularity=DAILY`, `Metrics=NetUnblendedCost`, `GroupBy=SERVICE`. API가 허용하는 가장 긴 과거 기간. 읽기 전용 사용자로 호출하고, 요청 수와 비용을 기록한다 |
| 알려진 변경 (라벨) | 계정 소유자 확인과 콘솔 조회 결과: 이 기간 동안 상시로 요금이 난 자원은 Secrets Manager 시크릿 1개뿐이고, 마지막 날에 삭제 예약했다. 그 밖의 의도적인 사용 증가는 없다 |
| 판정 방법 | 알려진 변경으로 설명되지 않는 경보는 오탐으로 본다. 경보마다 날짜 위치(월 첫날·마지막 날 여부), 서비스, `Estimated` 여부를 사람이 검토한다 |
| 기준값 결정 규칙 | 이 데이터에는 실제 급증 라벨이 없으므로 **기준값을 이 데이터로 조정하지 않는다.** 결과는 기준값마다 "유지(오탐 없음)" 또는 "보류(오탐 패턴 관찰, 실제 프로젝트 데이터로 다시 확인)"로만 기록한다. 조정·평가 기간 분할은 조정을 하지 않으므로 적용하지 않는다 |
| 비공개 처리 | 원본 응답은 저장소 밖 폴더(계정 소유자의 로컬 문서 폴더)에 둔다. 저장소에는 서비스별 일수, 경보 수, 경보의 상대 위치(시계열 시작 기준 일차), 관측값 ÷ 기준 중앙값 비율만 남긴다. 금액·날짜·계정 식별자는 남기지 않는다 |
| 비용 상한 | Cost Explorer 요청당 0.01 USD, 최대 10건(0.10 USD) |

## 실행

```powershell
# 원본은 저장소 밖에 둔다. 읽기 전용 프로필로 1회 요청.
aws ce get-cost-and-usage --profile cel-readonly --region us-east-1 --granularity DAILY --metrics NetUnblendedCost --group-by Type=DIMENSION,Key=SERVICE --time-period Start=<시작>,End=<끝> > <저장소 밖>\page1.json
py -3 -B experiments/023-real-cost-spike-check/check.py <저장소 밖>\page1.json > experiments/023-real-cost-spike-check/result.json
cd experiments/023-real-cost-spike-check; py -3 -B test_check.py
```

[result.json](result.json)에는 금액·날짜·계정 식별자 없이 서비스별 일수, 경보 수, 경보의 상대 위치(첫날 기준 일차), 월 첫날·마지막 날 여부, 잠정 여부, 관측값 ÷ 기준 중앙값만 남겼다.

## 결과

데이터는 410일이고, 마지막 14일은 `Estimated`(잠정)였다. 응답에 나온 서비스는 Secrets Manager, S3(전 기간 0), Tax 셋이다.

| 시계열 | 경보 | 원인 (사람 검토) | 판정 |
|---|---:|---|---|
| Secrets Manager | 14 (연속) | 월 고정 요금이 하루 단위로 나뉘어, 28일인 2월은 하루 요금이 31일 달보다 **10.7%** 높다. MAD가 0이라 10% 하한이 기준이 되고, 28일 창의 중앙값이 바뀔 때까지 14일 동안 경보가 이어졌다. 30일 달(+3.3%)에는 경보가 없었다 | 오탐 |
| Tax | 13 (매달 1회) | 세금은 매달 첫날에만 붙는다. 평소 중앙값이 0이라 0보다 큰 값이면 모두 경보가 된다 | 오탐 |
| S3 | 0 | 전 기간 0 | — |
| 서비스 합계 | 26 | 위 두 패턴의 합. 세금이 붙는 날은 합계가 평소의 약 5배다 | 오탐 |

알려진 변경(마지막 날의 시크릿 삭제 예약)은 비용 감소라서 상승만 보는 규칙에는 잡히지 않았다. 질문에 대한 답:

1. **예.** 실제 급증이 없는 계정에서 서비스별 27건, 합계 26건의 경보가 났다. 모두 오탐이다.
2. **예.** 모든 경보가 월 경계(첫날)에서 시작했다. 세금은 월 첫날 청구, Secrets Manager는 2월의 일수 차이가 원인이다. 합성 실험 021은 두 패턴을 만들지 않았다.
3. **예.** 비용이 일정한 서비스에서는 MAD가 0이라 10% 하한이 사실상 유일한 기준이다. 그런데 이 하한은 2월의 일수 효과(10.7%)보다 낮다.

## 기준값 판정 (사전에 정한 규칙: 조정하지 않고 유지 또는 보류)

| 기준값 | 판정 | 근거와 다시 확인할 점 |
|---|---|---|
| `cost.min_relative_increase` (10%) | **보류** | 월 고정 요금의 2월 효과(+10.7%)가 하한을 넘어 오탐을 냈다. 고칠 수 있는 방향은 세 가지다: 하한을 11% 넘게 올리기, 일 비용을 해당 월 일수로 보정하기, 같은 달 비교. 이 데이터로는 고르지 않는다 |
| `cost.mad_k` (3) | **보류** | 경보가 모두 MAD=0인 시계열에서 났으므로 k가 관여한 경보가 없다. 판단할 근거가 없다 |
| `cost.window_days` (28) | **보류** | 2월 효과가 창 길이의 절반(14일) 동안 이어졌다. 창 길이와 오탐 지속의 관계만 확인했다 |
| `cost.exclude_alerts` (false) | 유지 | 기본값 그대로 실행했다. 제외 설정을 켰다면 2월 이후에도 경보가 이어졌을 수 있다(021의 폭주) |

**규칙 자체의 빈틈 2가지.** 기준값 조정과는 별개로, 실제 프로젝트 데이터에서 다시 확인할 점이다.
- **중앙값 0 처리**: 평소 0인 시계열(세금, 가끔 쓰는 서비스)은 작은 금액에도 매번 경보가 난다. 최소 금액 하한이나 세금·크레딧 행을 분리하는 처리가 필요하다.
- **소액 표시 정밀도** (024에서 소수 넷째 자리로 수정): InfraFit 대기열은 금액을 소수 둘째 자리로 표시했다. 그래서 하루 1센트 남짓인 시계열에서는 관측값과 기준이 같은 값(예: 0.01)으로 보인다. 판정은 반올림 전 값으로 하므로 결과는 맞지만, 사람이 검토할 때 혼동된다.

## 한계

- 실제 급증이 한 번도 없는 아주 작은 계정이다. 재현율·탐지 지연은 평가할 수 없고, 오탐 패턴만 확인했다.
- 서비스가 셋뿐이고 금액이 매우 작다. 실제 프로젝트(IoT·Firehose·Bedrock)의 사용량 변동은 이 데이터에 없다.
- 마지막 14일은 잠정 값이다.
