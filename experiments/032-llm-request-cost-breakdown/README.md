# 032 — LLM 요청 1건당 비용 분해와 호출 증폭

[실험 목차](../README.md) · [Bedrock 노트 추가 절](../../studies/aws/bedrock/README.md#추가2026-11-15--guardrails-텍스트-단위-knowledge-base-저장-최소-요금-모델-배분) · [020 프롬프트 캐싱](../020-bedrock-token-caching/README.md)

**재현 PASS. H1·H2 지지, H3 기각. 모델 배분은 비용만 계산하고 판정 보류.** 챗봇 요청 1건의 비용을 모델 토큰·Guardrails·벡터 저장소 최소치·API로 나누고, 에이전트가 한 요청에서 모델을 여러 번 부를 때 비용이 얼마나 커지는지, 프롬프트 캐싱이 얼마나 줄이는지 계산했다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 챗봇 요청 1건 비용에서 모델 토큰은 몇 %인가? 에이전트 호출 k회는 단일 호출의 몇 배인가? 고정 앞부분 캐싱은 얼마나 줄이는가? |
| 가설 H1 | 시나리오 ② 챗봇 요청 1건 비용에서 모델 토큰이 50% 미만이다. |
| 가설 H2 | 시나리오 ① 에이전트 요청(호출 4회)은 단일 호출 비용의 4배를 넘는다(앞선 도구 결과가 다음 호출 입력에 쌓이므로). |
| 가설 H3 | 시스템 프롬프트·도구 정의(2,000토큰)를 캐시하면 에이전트 요청 비용이 20% 이상 준다. |
| 챗봇 | Claude Haiku 4.5, 입력 1,500·출력 400 토큰, 질문 200자·응답 1,500자에 Guardrails 콘텐츠 필터·거부 주제(입출력 각각), 벡터 저장소 OpenSearch Serverless Classic 최소 2 OCU를 월 질문 5만 건에 나눔, HTTP API 1건 |
| 에이전트 | Claude Haiku 4.5. 호출 i의 입력 = 시스템·도구 2,000 + 질문 100 + (i − 1) × (도구 결과 800 + 출력 300), 출력 300. 요청당 Athena 질의 2회 × 50 MB |
| 캐싱 | 고정 앞부분(체크포인트를 시스템·도구 뒤에) / 자동 캐싱(체크포인트가 입력 끝으로 이동). **체크포인트당 최소 토큰: Haiku 4.5 = 4,096, Haiku·Sonnet 5.5 = 512**(Bedrock 문서, 2026-11-15 확인). 요청 안에서만 재사용하고 요청 간 재사용은 넣지 않음 |
| 모델 배분 | 100% Sonnet 5.5 / Haiku 5.5 70% + Sonnet 5.5 30% / 100% Haiku 4.5 — **비용만 계산, 품질 판정 보류** |
| 요율 | [2026-11-15 사본](../../references/aws-price-list-apn2-2026-11-15.json) AmazonBedrockFoundationModels(게시일 2026-11-09), AmazonBedrock Guardrails, AmazonES, AmazonApiGateway, AmazonAthena |

H3는 처음에 최소 캐시 길이를 고려하지 않고 계산해 23% 절감이 나왔다. 결과를 정리하기 전에 Bedrock 문서에서 Haiku 4.5의 최소치(4,096)를 확인했고, 2,000토큰 앞부분은 캐시되지 않으므로 계산을 고쳤다. 가설 문장은 바꾸지 않았다.

판정: **판단 보류** — 배분에 따라 응답 품질이 유지되는지 평가할 데이터가 없다.

- **H1 지지**: 모델 토큰은 요청 비용의 27%였다. 가장 큰 몫은 벡터 저장소 최소 OCU(66%)였다([030](../030-hidden-minimum-charges/README.md)과 같은 결론).
- **H2 지지**: 호출 4회는 단일 호출의 5.83배였다. 입력 토큰이 호출 수의 제곱에 가깝게 늘어(앞선 도구 결과·출력이 쌓임) 8회면 16.6배다.
- **H3 기각**: Haiku 4.5에서 2,000토큰 앞부분은 최소치(4,096) 미달이라 캐시되지 않았다(절감 0%). 자동 캐싱은 누적 입력이 4,096을 넘는 3번째 호출부터 작동해 4회에서 12%였고, 3회에서는 쓰기만 하고 끝나 오히려 7.6% 비쌌다.

## 해석

- LLM 요청 비용 규칙은 모델 토큰만 보면 안 된다. **요청당 고정·최소 비용(벡터 저장소, KB 저장)과 Guardrails 텍스트 단위**를 같은 표에 넣어야 한다.
- 에이전트 비용은 호출 수에 선형이 아니다. 판단 자료: 요청당 모델 호출 수 분포, 호출별 입력 토큰(누적 맥락). 호출 수 상한·도구 결과 요약은 비용 수단이지만 품질 영향은 따로 평가해야 한다.
- 캐싱 절감은 **모델별 최소 캐시 길이**에 막힐 수 있다. InfraFit 규칙 후보: "캐시 체크포인트를 둔 앞부분 길이 < 모델 최소치 → 캐시가 작동하지 않음"(공식 자료). 같은 앞부분이라도 모델을 바꾸면 결론이 뒤집힌다.

## 가정·제외·한계

- 캐시 적중은 보장되지 않는다(다른 서버가 처리하면 새로 씀). 이 계산은 요청 안의 모든 호출이 적중한다는 상한이다. 요청 간 재사용(앞부분이 같은 다른 요청)은 [020](../020-bedrock-token-caching/README.md)에서 다뤘다.
- KB 관리형 저장 요금(사본 `missing`), 임베딩 모델 비용, 재시도·실패 호출은 넣지 않았다.
- Haiku 5.5와 Sonnet 5.5의 요율은 사본에 있는 그대로다. 모델 배분의 품질은 평가하지 않았다.
