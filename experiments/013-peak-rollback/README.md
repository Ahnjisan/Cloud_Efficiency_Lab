# 013 — 피크 품질 악화 후 CPU 한도 롤백

[실험 목차](../README.md) · [최종 연구 보고서](../../FINAL-REPORT.md)

**로컬 Docker 실측 PASS.** 전용 컨테이너 한 개에서 같은 HTTP 작업을 유지하고 CPU 한도만 **1.0 → 0.25 → 1.0**으로 바꿨다. 변경 전후 cgroup의 `cpu.max`는 각각 `100000 100000`, `25000 100000`, `100000 100000`이었다. 복원은 실험 순서에 미리 포함했다. 운영 자동 롤백은 실행하지 않았다. [실행 코드](run.py) · [부하 설정](load.js) · [실측 원본](live-result.json)

각 구간은 목표 25회/초, 12초, 최대 3 VU였다. 기준은 전송 요청 p99 200ms 이하, HTTP 오류율 1% 이하, 제공 부하 대비 성공률 99% 이상으로 고정했다. 제공 부하의 분모는 전송 요청과 미시작 반복의 합이다.

| 구간 | CPU | p99 | 성공 / 제공 | 성공 req/s | 미시작 | 품질 기준 |
|---|---:|---:|---:|---:|---:|---|
| 기준 | 1.0 | 104.31ms | 298 / 301 | 24.77 | 3 | 통과 |
| 축소 후보 | 0.25 | 893.47ms | 69 / 301 | 5.61 | 232 | 위반 |
| 기준 복원 | 1.0 | 35.85ms | 300 / 300 | 25.00 | 0 | 통과 |

전송된 요청의 HTTP 오류율은 세 구간 모두 0%였다. 축소 구간에서는 p99와 제공 부하 대비 성공률이 기준을 위반했고, 복원 후 첫 부하 창에서 두 기준을 다시 충족했다. 복원 명령 호출부터 해당 창의 관측 완료까지 약 12.69초였으며, 명령·부하 실행·관측 시간을 포함한다. 창 안에서 기준을 최초로 회복한 시각은 측정하지 않았다.

Windows, Docker 서버 29.8.2, k6 2.3.0에서 실행했다. 로컬 Docker 연결에 고정하고 기존 이미지로 전용 컨테이너만 생성했다. 서비스는 루프백에만 게시했고 메모리는 384 MiB로 제한했다. 시작 여유는 2.55 GiB였고, 부하 중 0.5초 간격으로 관측한 최저 여유는 2.49 GiB였다. 실행 후 전용 자원 정리와 기존 컨테이너 ID·상태 목록의 일치를 확인했다. Kubernetes 명령은 사용하지 않았다.

재실행은 저장소 루트에서 `py -3 -B experiments/013-peak-rollback/run.py`로 한다. 원본을 덮어쓰지 않도록 새 경로에 stdout을 기록한다. 이번 실측은 동일 순서 한 번에 한정된다. 반복 편차, 부하 발생기와 서비스 병목의 분리, Kubernetes 롤아웃·Pod 교체, EC2·EBS 데이터 복구 및 RTO·RPO, 실제 청구 변화는 미검증이다. [가상 EC2·EBS 롤백 사례](../../studies/methods/ec2-ebs-case-study.md)
