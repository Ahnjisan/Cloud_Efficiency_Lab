# 019 — 센서 파이프라인의 1,000건당 비용과 데이터 신선도

**계산 재현 PASS. H1 기각(쿼리량에 따라 바뀜), H2·H3 지지.** [016](../016-iot-message-batching/README.md)·[017](../017-firehose-buffer-small-files/README.md)·[018](../018-format-partition-scan/README.md)의 저장된 결과와 [서울 Price List 사본](../../references/aws-price-list-apn2-2026-11-13.json)을 읽어, 센서 → IoT Core → Firehose → S3 → Glue/Athena 파이프라인의 월 비용을 단계별로 나누고 센서 측정값 1,000건당 비용으로 바꿨다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 측정값 1,000건이 수집부터 분석까지 가는 비용은 어떤 항목으로 이뤄지고, 어느 설정이 가장 크게 좌우하는가? 개선 구성은 신선도를 얼마나 희생하는가? |
| 가설 H1 | 기준 구성에서 비용 1위는 IoT Core이며 전체의 50%를 넘는다(중심 쿼리량 기준). |
| 가설 H2 | 개선 구성의 1,000건당 비용은 기준 구성의 20% 이하다(중심 쿼리량 기준). |
| 가설 H3 | 수집부터 조회 가능까지의 최대 신선도는 약 60초에서 약 490초로 나빠진다. |
| 작업량 | 센서 100대, 10초마다 200 B, 30일 = 2,592만 건 (016·017 작업량 A) |
| 기준 구성 | 개별 IoT 메시지, 측정값 1건 = Firehose 레코드 1건, 버퍼 60초, CSV 원본(파티션 없음), 매일 Glue 크롤러(요금 페이지 예제의 2 DPU, 하루 10분 가정) |
| 개선 구성 | 20건 묶음, 묶음 1개 = 레코드 1건, 버퍼 300초, Firehose Parquet 변환 + `dt=` 접두사(018의 5분 파일 배치), 파티션 프로젝션(크롤러 없음) |
| 쿼리량 (가정) | 하루 Q1 100회, Q2 100회, Q3 1회, Q4 10회, Q5 1회. 측정값이 아니므로 0, 0.1, 1, 10배로 민감도를 봄 |
| 통제 조건 | 같은 작업량, 같은 요율, 무료 제공량·세금 제외, S3는 한 달치 보관 |
| 데이터 | 016~018의 결과 파일. 018은 432만 행 기준이라 읽은 바이트·저장 크기를 행 수 비율(6배)로 늘림 |

신선도는 디바이스 묶음 대기와 Firehose 버퍼 대기의 합이다. 기준 구성은 파티션 없는 테이블이라 새 객체가 바로 조회되고, 개선 구성은 파티션 프로젝션이라 파티션 등록을 기다리지 않는다고 보았다. 네트워크·S3 쓰기·쿼리 실행 시간은 넣지 않았다.


- **H1 기각**: 중심 쿼리량에서는 CSV 전체 스캔이 쿼리마다 약 1.57 GB(과금 1,495 MB)라 **Athena가 1위(45.34 USD)**였고 IoT 비중은 42.9%였다. 쿼리량이 중심의 10% 이하일 때만 IoT Core가 50%를 넘었다. 어느 설정이 가장 큰지는 **쿼리량 가정에 따라 바뀐다.**
- **H2 지지**: 개선 구성은 기준의 3.3%였다. 모든 쿼리량 배수에서 6% 이하였다.
- **H3 지지**: 최대 신선도가 60초에서 **490초**(묶음 190초 + 버퍼 300초)로, 평균은 30.5초에서 245.4초로 늘었다.
- 개선 구성에서는 IoT Core(2.44 USD, 그중 연결 0.41)가 여전히 가장 크다. 쿼리량을 10배로 늘려도 Athena는 3.40 USD였다.

## 해석

- 기준 구성의 낭비는 두 곳에 몰려 있다. **작은 메시지·레코드의 5 KB 계량**(IoT 40.85 + Firehose 4.45)과 **CSV 전체 스캔**(쿼리량에 비례)이다. 앞쪽은 업무량에 비례하고, 뒤쪽은 분석 사용량에 비례한다. 판정에는 메시지 크기뿐 아니라 **실제 쿼리 기록**이 필요하다.
- 개선 구성은 비용을 97% 줄이지만, 데이터가 최대 8분 넘게 늦게 보인다. 실시간 경보 경로가 이 파이프라인에 섞여 있으면 개선 구성을 그대로 쓸 수 없다. 경보용 토픽을 따로 두는 설계를 검토할 수 있다(비용 미계산).
- 네 가지 변경을 함께 적용한 결과다. 변경별 기여는 표의 항목별 차이로만 읽어야 하며, 서로 독립이라는 보장은 없다.

## 가정·제외·한계

- 쿼리량은 가정값이다. 실제 대시보드 갱신 주기와 쿼리 형태에 따라 Athena 비용이 크게 달라진다.
- 018의 읽은 바이트를 행 수 비율로 늘렸다. 5분 파일 배치의 footer 바이트는 파일 수가 같으므로 실제로는 늘지 않는다. 따라서 개선 구성의 Athena 비용은 과대 추정이다.
- 크롤러 실행 시간(10분)과 DPU(2)는 가정이다. Glue 최소 과금 시간은 확인하지 못했다.
- CloudWatch 로그·지표, KMS, 데이터 전송, Athena 결과 저장 S3 비용, IoT 디바이스 섀도·레지스트리는 제외했다.
- 무료 제공량을 제외했다. 첫 12개월 IoT 무료 제공량(메시지 50만 건 등)은 개선 구성의 IoT 비용을 더 낮출 수 있다.
