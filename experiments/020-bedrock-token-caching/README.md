# 020 — Bedrock 에이전트의 토큰 구성과 프롬프트 캐싱 손익분기

[실험 목차](../README.md) · [최종 연구 보고서](../../FINAL-REPORT.md) · [Bedrock 학습 노트](../../studies/aws/bedrock/README.md)

**시뮬레이션 재현 PASS. H1·H2 지지, H3 기각.** 에이전트 1회 실행의 모델 호출 수와 토큰 구성을 가정하고, 고정 앞부분(지시문·도구 스키마)을 캐싱하기 전후의 비용을 비교했다. 요율은 [서울 Price List 사본](../../references/aws-price-list-apn2-2026-11-13.json)의 Claude Haiku 5.5·Sonnet 5.5 **Global 교차 리전 추론** 요율이다(AmazonBedrockFoundationModels 게시일 2026-11-09). AWS 호출은 없다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 에이전트의 반복되는 앞부분을 캐싱하면 언제 이득이고 언제 손해인가? 하루 호출 수와 앞부분 길이 중 무엇이 결정하는가? |
| 가설 H1 | Haiku 5.5에서 실행당 호출이 2회 이상이면 5분 캐싱은 하루 실행 수와 무관하게 캐싱 없음보다 싸다(캐시 미스 0). 한 조합이라도 비싸면 기각한다. |
| 가설 H2 | 캐싱이 손해인 경우는 실행당 호출이 1회일 때뿐이다. 호출 2회 이상에서 손해가 하나라도 있으면 기각한다. |
| 가설 H3 | 1시간 TTL이 5분 TTL보다 유리한 경우는 실행 간 평균 간격이 5~60분일 때뿐이다. 그 밖의 간격에서 1시간이 0.1%p 넘게 유리한 조합이 있으면 기각한다. |
| 기준선 | 캐싱 없음 |
| 바꿀 변수 | 모델 {Haiku 5.5, Sonnet 5.5}, 실행당 호출 k {1, 2, 4, 8}, 고정 앞부분 P {500, 1,000, 3,000, 8,000} 토큰, 하루 실행 수 {10, 30, 100, 300, 1,000, 10,000}, 정책 {없음, 5분, 1시간}, 캐시 미스 확률 {0, 0.2} |
| 통제 조건 | 사용자 입력 500, 호출마다 관찰 500·출력 300 토큰 누적, 하루 12시간 활동, 14일, 호출 간격 5초, 고정 앞부분만 캐싱 |
| 데이터 | 합성. 실행 도착은 포아송 과정 |
| 시드·반복 | 시드 1·2·3, 결과는 평균과 범위 |

캐시 모형: 직전 읽기·쓰기 후 TTL 안에 오면 읽기, 아니면 쓰기이며, 적중할 때마다 TTL이 갱신된다. 미스 확률은 다른 서버(다른 리전 포함)가 처리해 새로 쓰는 경우를 나타낸다. Claude 5.5 계열의 최소 캐시 길이 512토큰보다 짧은 앞부분은 캐시하지 않는다.

## 결과

### 해석적 손익분기 — 필요한 적중률

앞부분 호출 중 캐시 읽기 비율이 `(쓰기 요율 − 입력 요율) ÷ (쓰기 요율 − 읽기 요율)`보다 높아야 캐싱이 이득이다. 앞부분 길이와 무관하다.

| 모델 | 5분 TTL | 1시간 TTL |
|---|---:|---:|
| Haiku 5.5 (입력 0.10, 쓰기 0.125/0.20, 읽기 0.01 USD/100만) | **21.7%** | 52.6% |
| Sonnet 5.5 (입력 2.00, 쓰기 2.50/4.00, 읽기 0.10) | **20.8%** | 51.3% |

### 앞부분 3,000토큰, 미스 0

| 모델 | 호출 | 하루 실행 | 없음 (USD/실행) | 5분 | 1시간 | 5분 절감 | 1시간 절감 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Haiku 5.5 | 1 | 10 | 0.000500 | 0.000543 | 0.000491 | **−8.6%** | 1.7% |
| Haiku 5.5 | 1 | 1,000 | 0.000500 | 0.000231 | 0.000231 | 53.9% | 53.9% |
| Haiku 5.5 | 4 | 10 | 0.00248 | 0.00171 | 0.00166 | 31.0% | 33.0% |
| Haiku 5.5 | 4 | 1,000 | 0.00248 | 0.00140 | 0.00140 | 43.5% | 43.5% |
| Sonnet 5.5 | 1 | 10 | 0.0100 | 0.0108 | 0.0097 | **−8.3%** | 3.4% |
| Sonnet 5.5 | 4 | 1,000 | 0.0496 | 0.0268 | 0.0268 | 45.9% | 45.9% |

호출 4회·하루 1,000회를 월로 환산하면 Haiku 5.5는 74.40 → 42.02 USD, Sonnet 5.5는 1,488 → 804 USD다(가정 작업량 기준).

- **H1 지지**: Haiku 5.5, 호출 2회 이상, 미스 0의 모든 조합에서 5분 캐싱이 쌌다. 최소 절감은 **11.1%**였다.
- **H2 지지**: 손해가 난 조합은 모두 호출 1회였다. 5분 TTL은 하루 10회(−8.6%)·30회(−2.3%, Haiku)에서 손해였고, 미스 0.2에서는 1시간 TTL도 하루 10회에서 손해(−11.5%, Haiku)였다. 앞부분 3,000토큰·미스 0.2·하루 10회에서도 호출 2회 이상이면 5분 TTL이 13.7% 이상 절감됐다.
- **H3 기각**: 미스가 없으면 1시간 TTL은 모든 하루 실행 수에서 5분보다 같거나 유리했다. 평균 간격 2.4분(하루 300회)에서도 53.6% 대 45.3%로 1시간이 앞섰고, 평균 간격 72분(하루 10회)에서도 1시간만 이득이었다. 포아송 도착에서는 평균 간격이 짧아도 5분을 넘는 간격이 섞이기 때문이다. 반대로 **미스 0.2에서는 114개 조합에서 5분이 1시간보다 유리**했다. 미스가 날 때마다 1시간 TTL은 입력의 2배 요율로 다시 쓴다. TTL 선택은 평균 간격보다 **간격 분포와 실제 캐시 미스율**에 달려 있다.
- 앞부분이 512토큰 미만(500)이면 모든 정책의 비용이 캐싱 없음과 같았다.
- 앞부분 길이는 절감 폭을 바꾼다. 호출 4회·하루 100회·미스 0에서 5분 TTL 절감은 P=1,000일 때 18.1%(Haiku), P=8,000일 때 54.3%였다.

## 해석

- 손익분기는 "하루 호출 수"가 아니라 **같은 앞부분 요청이 TTL 안에 다시 오는 비율**로 판단해야 한다. 실제 계정에서는 응답의 `cacheReadInputTokens`·`cacheWriteInputTokens` 합계로 적중률을 계산하고 21% 기준과 비교할 수 있다.
- 실행당 여러 번 호출하는 에이전트는 실행 안의 재사용만으로 이득이 나므로, 캐싱 미적용은 근거가 분명한 낭비 후보다. 반대로 단일 호출이 드물게 오는 기능에 캐싱을 켠 것은 손해일 수 있다.
- 1시간 TTL은 미스율을 모르면 판단을 보류한다. Global 교차 리전 추론은 수요가 높을 때 캐시 쓰기가 늘 수 있다고 AWS가 설명한다.

## 가정·제외·한계

- 대화가 누적되는 부분(이전 출력·관찰)은 캐싱하지 않았다. 체크포인트를 대화 끝으로 옮기는 자동 캐싱을 쓰면 절감이 더 커질 수 있다.
- 미스는 독립 확률로 단순화했다. 실제 미스는 부하·리전·서버 배치에 따라 몰려서 생길 수 있다.
- 출력 길이, 호출 수, 품질의 관계는 모형에 없다. 호출 수를 줄여 생기는 품질 저하는 이 실험으로 평가할 수 없다.
- Global 요율만 사용했다. 데이터 처리 위치 요구로 Geographic·리전 내 요율을 쓰면 금액은 달라지지만, 쓰기·읽기 비율이 같다면 손익분기 적중률은 그대로다(미확인 요율이므로 계산하지 않음).
- Long Context 요율, 배치 추론, AgentCore 자체 과금은 제외했다.
