# 005 — Docker 워크로드 자원 효율 실측

같은 HTTP 워크로드에서 CPU 한도 1.0과 0.5를 비교한다. 가설은 낮은 CPU 한도가 같은 부하에서 throttling을 늘리고 처리량이나 지연에 영향을 줄 수 있다는 것이다. 메모리 제한은 양쪽 512 MiB로 고정한다.

## 실행 조건

- Windows 11, Docker Engine 29.8.2, Python 3.14.7(호스트 실행), k6 2.3.0을 사용했다. [공유 HTTP 워크로드](../006-kubernetes-resource-efficiency/workload.py)는 고정 입력에 PBKDF2-SHA256을 70,000회 수행한다.
- [k6 설정](../006-kubernetes-resource-efficiency/load.js)은 목표 25회/초, 30초, 최대 3 VU다. 1.0 → 0.5 → 0.5 → 1.0 순으로 컨테이너를 하나씩 실행한다.
- 기존 로컬 Python 이미지를 digest로 지정하고 pull을 차단했다. 전용 브리지와 루프백 포트를 사용했으며, 읽기 전용 워크로드 파일 외에 기존 데이터를 연결하지 않았다.
- 사용자 요청으로 기존 5 GiB 기준 대신 이 소규모 순차 실행은 호스트 시작 하한 2.25 GiB, 실행 중 중단 하한 1.5 GiB를 적용했다. CPU·메모리·PID 상한과 명령 시한을 유지했다.

저장소 루트에서 `py -3 -B experiments/005-container-resource-efficiency/run_live.py`를 실행한다. [실행 코드](run_live.py) · [stdout 원본](live-result.json). k6 성공 처리량과 HTTP 오류율, 시작하지 못한 반복 횟수는 각각 기록한다. 컨테이너 CPU와 throttling은 부하 전후 cgroup 카운터 차이, 메모리는 cgroup의 관측값과 최고값을 사용한다.

현재 실행기는 선택한 Docker 컨텍스트를 확인한 뒤 지원하는 로컬 Windows named pipe에 연결을 고정한다. `DOCKER_HOST`가 설정되어 있거나 컨텍스트가 원격이면 실행을 중단한다. 생성 명령이 실패해도 실행 소유 라벨로 전용 컨테이너와 네트워크를 찾아 정리하고, 잔존 여부를 확인할 수 없으면 실패로 기록한다.

호스트 여유 메모리는 Windows `GlobalMemoryStatusEx`로 감시 대상 명령의 시작 직전과 실행 중 약 2초마다 샘플링한다. 1.5 GiB 미만을 관측하면 해당 명령을 시작하지 않거나 중단한다. 로그의 최저값은 샘플 중 최저값이다. 명령 사이와 HTTP 준비 대기 중에는 연속 감시가 없고, 정리 명령에는 메모리 중단 기준을 적용하지 않는다.

모든 구간에서 성공 요청, 유효한 지연·처리량, 설정과 일치하는 CPU quota, 전후 cgroup 카운터와 메모리 표본이 확인되어야 실행을 PASS로 기록한다. 목표 부하 충족은 `target_load_met`으로 별도 기록한다. 이 기준은 보존된 원본의 네 구간에 대해 [반례 테스트](../006-kubernetes-resource-efficiency/test_live_safety.py)로 검증했다.

## 결과

**PASS · 두 구성에서 각각 두 번 완료.** 시작 여유는 3.22 GiB였고, k6 실행 중 관측한 최저 여유는 3.16 GiB였다. 네 구간에서 전송된 요청의 HTTP 오류율은 0%, 재시작과 OOM kill은 0건이었다.

| 순서 | CPU 한도 | p95 / p99 (ms) | 성공 req/s | 시작하지 못한 반복 | CPU 사용 (CPU초) | throttling 구간 수 | cgroup 최고 메모리 (MiB) |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1.0 | 35.86 / 74.09 | 24.93 | 2 | 19.22 | 8 | 36.5 |
| 2 | 0.5 | 457.63 / 495.57 | 10.28 | 441 | 15.08 | 300 | 17.3 |
| 3 | 0.5 | 386.67 / 460.95 | 10.69 | 428 | 15.14 | 302 | 17.1 |
| 4 | 1.0 | 34.66 / 45.36 | 24.98 | 1 | 18.96 | 4 | 17.1 |

0.5코어 조건은 실제 CPU 사용량이 약 15 CPU초로 제한됐고 throttling과 완료된 요청의 꼬리 지연이 증가했다. 동시에 성공 처리량이 약 10~11 req/s로 떨어졌다. 부하 발생기의 3 VU 한도 때문에 시작하지 못한 반복이 크게 증가했다. p95·p99는 실제 전송한 요청을 기준으로 하므로 목표 25 req/s를 온전히 처리한 것으로 해석하지 않는다. 1코어 반복 간 p99도 달라 단일 지연값으로 일반화하기 어렵다.

메모리는 cgroup 최고값으로, 컨테이너 시작 이후 샘플 시점까지를 포함한다. 메모리 제한은 고정했으므로 메모리 제한 변경의 효과를 검증하지 않았다. 전용 컨테이너와 네트워크는 정리했다. AWS 가격·청구와 연결하지 않았다. 다음에는 격리된 호스트에서 부하 발생기 자체가 포화되지 않도록 설계한 뒤 반복 편차를 비교할 수 있다.
