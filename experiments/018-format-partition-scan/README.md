# 018 — 저장 형식·파티션별 스캔량 (대리 측정)

[실험 목차](../README.md) · [최종 연구 보고서](../../FINAL-REPORT.md) · [Athena·Glue 학습 노트](../../studies/aws/athena-glue/README.md)

**로컬 대리 측정 재현 PASS. H1 지지, H2 형식상 지지·내용상 기각, H3 부분 기각.** 같은 합성 센서 데이터를 CSV, CSV.gz, Parquet, Parquet+날짜 접두사의 5분 파일, Parquet+날짜/구역 파티션으로 저장하고, 대표 쿼리 5개가 읽어야 하는 바이트를 pyarrow 26.0.1로 계산했다.

> **이것은 Athena 실측이 아니다.** CSV는 프루닝되지 않은 파일 전체 바이트, Parquet은 프루닝되지 않은 파일의 footer와 행 그룹 통계로 건너뛰지 못한 열 덩어리의 압축 바이트를 더한 값이다. Athena의 실제 스캔량은 엔진의 읽기 단위, 페이지 인덱스, 메타데이터 읽기 방식에 따라 다를 수 있다. 과금 환산에는 Athena 규칙(메가바이트 올림, 쿼리당 최소 10 MB, 서울 5 USD/TB)을 적용했다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 저장 형식과 파티션이 대표 쿼리의 스캔량과 과금액을 얼마나 바꾸는가? |
| 가설 H1 | 하루·한 구역 평균 쿼리(Q1)에서 Parquet+날짜/구역 파티션은 CSV 대비 읽은 바이트를 90% 이상 줄인다. |
| 가설 H2 | 센서 하나의 모든 열을 읽는 쿼리(Q4)는 열 선택 이점이 없으므로 절감률이 Q1보다 작다(설계 때 표현: "효과가 작다"). |
| 가설 H3 | 이 데이터 규모(월 432만 행)에서 Parquet 계열 쿼리는 모두 10 MB 최소 과금에 걸려 과금액 차이가 사라진다. 코드에는 설계 당시 정한 두 배치(`parquet`, `parquet_dt_zone`)만 판정 대상으로 넣었다. |
| 기준선 | CSV, 파티션 없음(일별 파일 30개) |
| 바꿀 변수 | CSV.gz(레벨 6), Parquet(일별 파일, Snappy), Parquet 5분 파일(`dt=` 접두사, Firehose의 300초 버퍼와 같은 단위), Parquet `dt=`/`zone=` 파티션(구역·일별 파일) |
| 통제 조건 | 같은 행, 시간순 정렬, pyarrow 기본 행 그룹 크기, 같은 쿼리 정의 |

| 시드·반복 | 데이터 생성 시드 1·2·3. 결과는 최소·최대 범위 |

**설계 변경 기록.** 처음 실행한 소형 점검에서 일별 Parquet 파일만으로는 Firehose가 실제로 쓰는 "작은 파일"의 영향을 볼 수 없어, 결과를 보기 전에 5분 파일 배치와 파일별 footer 바이트를 추가했다. H3는 그 전에 정한 두 배치만 판정하도록 코드에 남아 있으며, 5분 배치의 결과는 아래에 따로 적는다.

쿼리 1회 과금액: CSV 250 MB = 0.00119 USD, CSV.gz 48 MB = 0.00023 USD, 10 MB 최소 = 0.0000477 USD. 세 시드의 범위 폭은 모든 칸에서 2% 미만이었다. 파티션 배치에서 Q1·Q4 결과 행이 전체 표와 일치함을 확인했다.

- **H1 지지**: Q1에서 날짜/구역 파티션은 CSV 대비 **99.99%** 줄었다.
- **H2 형식상 지지, 내용상 기각**: Q4 절감률(99.64%)은 Q1(99.99%)보다 작아 판정 기준은 충족했다. 그러나 Q4도 99% 넘게 줄어 "효과가 작다"는 설계 때 표현은 틀렸다. CSV는 프루닝 없이 30일 전체를 읽기 때문이다. 또 Q4에서는 날짜/구역 파티션(0.95 MB)이 파티션 없는 일별 Parquet(0.73 MB)보다 더 많이 읽었다. 구역별로 쪼갠 파일마다 footer와 사전(dictionary)이 따로 붙는다.
- **H3 부분 기각**: 판정 대상이던 두 배치는 모든 쿼리가 10 MB 최소에 걸렸다. 그러나 Firehose가 직접 쓰는 형태인 **5분 파일 배치에서는 Q3가 22 MB, Q5가 15 MB로 최소를 넘었다.** 8,640개 파일마다 footer와 열 사전을 읽어야 하기 때문이다.
- **작은 파일의 비용**: 같은 Parquet이라도 5분 파일은 일별 파일보다 저장 크기가 4.1배, 한 달 전체 쿼리(Q5)의 읽은 바이트가 71배였다. 반면 마지막 1시간 쿼리(Q2)는 일별 파일이 행 그룹 하나(하루 전체)라 시간 통계로 건너뛰지 못해, 5분 파일과의 차이가 1.7배로 작았다.
- CSV.gz는 CSV 대비 5.3:1로 줄었다. 요금 페이지가 예시한 "3:1"보다 컸지만, 반복이 많은 합성 데이터라는 점을 감안해야 한다.

## 해석

- CSV를 Parquet으로 바꾸는 효과는 압도적이었다. 그러나 이 규모에서는 Parquet 이후의 개선(파티션, 파일 합치기)은 대부분 **10 MB 최소 과금 아래**에서 일어나 금액 차이로 보이지 않는다.
- 금액이 아니라 **읽은 바이트와 파일 수**를 보면, Firehose의 작은 파일이 한 달 단위 쿼리를 크게 늘린다. 데이터나 쿼리가 커지면 작은 파일 합치기(compaction)나 버퍼 확대가 비용 문제로 바뀐다. 합치기의 Glue 비용은 측정하지 않았다.
- 파티션은 쿼리가 파티션 열로 거를 때만 효과가 있고, 너무 잘게 나누면 오히려 읽는 양이 늘 수 있다(Q4).

## 가정·제외·한계

- Athena 실측이 아니다. Athena가 footer를 몇 번 읽는지, 페이지 인덱스를 쓰는지, CSV를 압축 해제 전후 어느 크기로 과금하는지(이 실험은 압축 바이트로 계산)는 확인하지 않았다.
- 데이터가 규칙적인 합성 값이라 압축률이 실제보다 좋을 수 있다.
- 5분 파일은 Firehose의 Parquet 변환 결과를 흉내 낸 것이다. Firehose가 실제로 쓰는 행 그룹 크기·압축 코덱은 확인하지 않았다.
- S3 GET·LIST 요청 비용과 쿼리 지연은 측정하지 않았다(파일 수만 기록).
- 전체 실행은 약 31분이 걸려 단위 테스트에서 다시 돌리지 않는다. 대신 소형 데이터로 프루닝 규칙·결과 일치·결정성을 테스트한다.
