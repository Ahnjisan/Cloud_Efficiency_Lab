# 041 — 챗봇 조회 결과를 LLM에 얼마나 넘기나

[실험 목차](../README.md) · [032 LLM 요청 비용 분해와 호출 증폭](../032-llm-request-cost-breakdown/README.md) · [020 프롬프트 캐싱](../020-bedrock-token-caching/README.md) · [033 입력 토큰 정의](../033-input-token-definitions/README.md)

**재현 PASS. H1 기각(9.71배), H2 지지, H3 기각.** 실행 전 결정은 2026-11-27에 먼저 썼고, 실행 뒤 가설·판정 기준을 바꾸지 않았다.

챗봇의 오케스트레이터 에이전트가 하위 에이전트(검색·조회·분석)를 부르고, 조회 에이전트가 PostgreSQL 읽기 전용 SQL 결과를 Bedrock에 넘길 때, 결과를 몇 행·몇 열·어떤 형식으로 넘기느냐에 따라 질문 1건 비용과 컨텍스트 사용량이 어떻게 바뀌는지 계산한다. AWS를 호출하지 않는다. 결과 행은 합성이고, 문자→토큰 환산·호출 구조·질문 수는 **가정값**이다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | SQL 결과의 행 수·열 수·직렬화 형식·사전 집계 여부가 질문 1건 비용과 컨텍스트 사용량을 얼마나 바꾸는가? |
| 가설 H1 | 1,000행·전체 열·JSON으로 넘기면, SQL에서 미리 집계해 넘길 때보다 질문 1건 비용이 10배 이상이다(Haiku 4.5, 호출 4회, 캐싱 없음, 환산 보통). |
| 가설 H2 | 같은 행·열에서 JSON은 CSV보다 토큰이 30% 이상 많다(전체 열, 행 수 네 단계 모두). |
| 가설 H3 | 1,000행·전체 열·JSON이면 가장 큰 호출의 입력이 컨텍스트 한도 200K 토큰을 넘는다(환산 보통). |
| 합성 결과 행 | 12열: record_id, company_code, drawing_no, spec_item(한글 항목명), nominal, tol_plus, tol_minus, measured, unit, judgment(합격/불합격), inspector_id, measured_at. 시드 41. 실제 회사·고객 자료를 쓰지 않는다 |
| 바꿀 변수 | 행 수 10 / 50 / 200 / 1,000. 열: 전체 12열 / 필요한 5열(spec_item, nominal, measured, judgment, measured_at). 원본 행 / SQL 사전 집계(spec_item별 건수·불합격 수·평균·최솟값·최댓값·표준편차, 항목 10개). 형식 JSON(객체 배열) / CSV(머리글 포함). 호출 수 3 / 4 / 6. 캐싱 없음 / 자동 캐싱 |
| 토큰 환산 (가정) | ASCII 문자 ÷ 3.5 + 비ASCII(한글) 문자 × 1.0. 민감도: 적게(ASCII ÷ 4.0, 한글 × 0.7), 많게(ASCII ÷ 2.5, 한글 × 1.5). 실제 토크나이저로 세지 않았다 |
| 호출 구조 (가정, 032 방식) | 시스템·도구 2,000 + 질문 100 토큰이 매 호출에 들어가고, 앞선 호출의 도구 결과·출력이 뒤 호출 입력에 쌓인다. 호출 1(찾기) 도구 결과 200·출력 300, 호출 2(조회) 도구 결과 = SQL 결과·출력 300, 이후 호출은 출력 300. 호출 k회면 SQL 결과는 k − 2번 다시 입력된다 |
| 캐싱 | 자동 캐싱(체크포인트가 입력 끝으로 이동, 질문 안에서만 재사용). Haiku 4.5 최소 4,096토큰([032](../032-llm-request-cost-breakdown/README.md)에서 확인) |
| 모델·요율 | Claude Haiku 4.5(기준), Sonnet 4.5(민감도). [2026-11-15 사본](../../references/aws-price-list-apn2-2026-11-15.json)의 Global 교차 리전 요율. 리전 내 요율 확인 필요 |
| 컨텍스트 한도 | 200K 토큰(가정, 이번에 공식 문서로 재확인하지 않음) |
| 월 비용 | 하루 질문 50 / 200 / 1,000건 × 평일 22일. 질문마다 위 구조가 같다고 가정 |

**월 비용 (호출 4회, Haiku 4.5, 평일 22일)**

- **H1 기각**: 1,000행·전체 열·JSON은 사전 집계의 **9.71배**(0.1693 대 0.0174 USD)로 10배에 조금 못 미쳤다. 사전 집계 쪽도 매 호출에 들어가는 시스템·도구 프롬프트(2,100토큰 × 4회)가 바닥 비용을 만들기 때문이다. 호출 6회면 11.7배, 3회면 7.1배다.
- **H2 지지**: 같은 행·열에서 JSON은 CSV보다 토큰이 2.39~2.67배였다. 행마다 열 이름이 반복되기 때문이다(압축 구분자 JSON 기준).
- **H3 기각**: 1,000행·전체 열·JSON의 가장 큰 호출 입력은 79,444토큰으로 200K를 넘지 않았다. 이 실험의 조건에서 한도를 넘는 경우는 없었다. 같은 형식이면 약 2,580행(환산 보통) 또는 1,830행(환산 많게)부터 한 호출이 한도를 넘는다.
- 호출 수가 늘면 SQL 결과가 뒤 호출마다 다시 입력돼 비용이 거의 비례로 는다(1,000행 JSON: 3회 0.088 → 6회 0.332 USD).
- 자동 캐싱은 결과가 큰 경우(200행 이상)에 16~30%를 줄였고(결과가 클수록 큼, 1,000행·전체 열·JSON 30.3%), 결과가 작아 누적 입력이 4,096토큰(Haiku 4.5 최소) 미만이면 효과가 없었다.

## 해석

- 조회 AI가 넘기는 결과의 **모양**이 질문 비용을 정한다. 순서대로 효과가 큰 것은 (1) SQL에서 미리 집계하기, (2) 필요한 열만 넘기기, (3) JSON 대신 CSV(표 형식)로 넘기기, (4) 뒤 호출로 원본 결과를 다시 넘기지 않기(요약만 넘기기)다.
- 행 수가 작으면(50행 이하) 결과 모양보다 고정 프롬프트가 비용을 정한다. 이때는 호출 수와 시스템 프롬프트 길이를 먼저 본다.
- 컨텍스트 한도보다 비용이 먼저 문제가 된다. 하루 1,000건이면 원본 1,000행 JSON 방식은 월 3,724 USD로, 사전 집계(384 USD)와 3,300 USD 넘게 차이 난다.
- InfraFit 규칙 후보(후보): "조회 결과 토큰이 질문 입력의 50% 이상이고 행 수가 N 이상" → 사전 집계·열 축소 검토. "같은 SQL 결과가 한 질문 안에서 2회 이상 입력됨" → 호출 증폭 검토.

## 가정·제외·한계

- 토큰 수는 문자 수 환산 가정(ASCII ÷ 3.5, 한글 × 1.0)이며 실제 토크나이저로 세지 않았다. 출처마다 입력 토큰 정의가 다르다([033](../033-input-token-definitions/README.md): Converse는 캐시 제외, Responses는 포함, CloudWatch는 미확인). 이 실험의 "입력 토큰"은 캐시 여부와 무관한 전체 입력이다.
- 호출 구조(4개 AI, 출력 300토큰, 결과가 뒤 호출에 그대로 쌓임)는 가정이다. 실제 챗봇이 결과를 요약해 넘기면 증폭은 줄어든다.
- 합성 행의 값 길이(도면 번호, 날짜 형식)가 토큰 수에 영향을 준다. 컨텍스트 한도 200K는 이번에 재확인하지 않았다.
- Bedrock 요율은 Global 교차 리전 행이다. 국내 처리 요율은 확인 필요.
