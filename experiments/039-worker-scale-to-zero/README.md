# 039 — 워커 상시 실행 vs KEDA 0까지 축소

[실험 목차](../README.md) · [031 컨테이너 실행 방식별 비용](../031-container-runtime-cost/README.md) · [029 상시 고정비](../029-fixed-cost-scheduling/README.md) · [015 Minikube 실측 절차](../015-kubernetes-rollback/README.md)

**실측 및 정리 PASS, 계산 재현 PASS. H1·H2·H3 지지.** 실행 전 결정은 2026-11-27에 먼저 썼고, 실행 뒤 가설·판정 기준을 바꾸지 않았다. KEDA는 설치하지 않았고 파드 시작 시간만 실측했다.

structurer-worker(Python, EKS Deployment)를 KEDA로 0개까지 줄이면 실제로 얼마를 아끼고, 첫 결과가 얼마나 늦어지는지를 계산한다. 파드 시작 시간만 로컬 Minikube에서 실측한다. AWS를 호출하지 않는다. 작업량·처리 시간·노드 기동 시간은 **가정값**이다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 워커를 0개까지 줄이면 월 비용이 얼마나 줄고, 첫 결과 지연은 얼마나 늘어나는가? |
| 비교 | W1 워커 1개 상시. W2 KEDA 최소 0(pollingInterval 30초, cooldownPeriod 300초 기본, 변수로 15·60초 / 120·600초). W3 최소 0 + 평일 08~18시만 최소 1 |

| 가설 H1 | (a)에서 W2·W3의 EC2 절감은 작업량 세 단계 모두 0 USD다. |

| 가설 H3 | (b1)에서 W2의 "꺼진 상태에서 도착한 측정지"의 첫 결과 지연 평균은 W1 평균의 3배 이상이다. |

| 처리 (가정) | 워커 1개가 순서대로 처리, 장당 로그정규 중앙값 20초(σ 0.5). 최대 복제 1(500장/일도 1개로 감당: 약 2.8시간) |
| 지연 모형 | W1: 워커가 계속 받으므로 대기 없음 + 처리. W2(꺼진 상태 도착): 다음 폴링까지 대기 + 파드 시작(실측) + (b1) 노드 기동 + (b2) Fargate 파드 기동 + 처리 |

AWS 문서는 "노드가 쓸 수 있게 되기까지 몇 분 걸릴 수 있다"고만 적고 숫자를 주지 않는다([EKS Best Practices — Cluster Autoscaler](https://docs.aws.amazon.com/eks/latest/best-practices/cas.html), 2026-11-27 확인). Fargate 파드 기동 60초(민감도 30·120초), 출처 없는 가정. 전용 노드는 파드가 사라진 뒤 10분 뒤 제거(Cluster Autoscaler 축소 대기로 알려진 기본값, 이번에 재확인 안 함 → 가정, 민감도 0분) |
| 과금 | (b1) 노드가 떠 있는 초 단위(EC2 Linux 초 단위 과금·최소 60초는 이번에 재확인 안 함 → 가정). (b2) Fargate는 이미지 다운로드 시작부터 파드 종료까지 초 단위, 최소 1분(공식, 2026-11-15 확인). 월 30일 = 720시간. 요율은 [2026-11-15 사본](../../references/aws-price-list-apn2-2026-11-15.json) |
| 시드 | 도착·처리 시간 시드 1·2·3 |
| 실측 질문 | 작은 Python 컨테이너 Deployment를 0 → 1로 늘렸을 때 Ready까지 걸리는 시간. 노드 안 이미지 캐시 있음/없음 각 5회 |
| 실측 환경 | 전용 Minikube 프로필(docker 드라이버, 노드 메모리 2,048 MiB·CPU 2), 별도 kubeconfig, 전용 네임스페이스 `cel-039`. 이미지 `python:3.12-alpine`(imagePullPolicy IfNotPresent), readinessProbe exec `true`(1초 간격). **KEDA는 설치하지 않고** `kubectl scale`로 파드 시작 시간만 잰다 |
| 실측 순서 | 캐시 없음·있음을 번갈아 5쌍(없음 먼저). 캐시 없음은 매회 노드 안에서 이미지를 지운다. 측정값 = `kubectl scale` 명령 시작부터 Ready 확인까지의 벽시계 시간(약 0.3초 간격 폴링), 교차 확인으로 파드의 생성 시각 → Ready 전이 시각(1초 해상도)도 기록 |
| 실측 안전 | 시작 여유 메모리 4 GiB 이상(불충분하면 미실행 기록), 실행 중 1.5 GiB 미만이면 중단. 시작 전후 호스트 컨테이너 ID·상태 목록 비교. 끝나면 네임스페이스·프로필 삭제(노드 안 이미지 함께 삭제), 호스트 이미지 목록 비교. 실패하면 중단하고 그대로 기록 |

## 해석

- 워커를 0으로 줄이는 이득은 **노드 구성에 달렸다.** 다른 서비스와 노드를 함께 쓰면 파드를 꺼도 청구는 그대로다([031](../031-container-runtime-cost/README.md)과 같은 결론). 절감을 원하면 워커를 Fargate나 전용 노드 그룹으로 분리해야 하고, 그 대가가 첫 결과 지연이다.
- 비용과 지연을 함께 보면 **W3(근무 시간만 최소 1) + Fargate**가 균형점이다. 근무 시간 도착분은 지연이 W1과 거의 같고(전체 평균 26~31초), 월 비용은 W1의 31~36%다. 근무 시간 밖 도착분만 약 96초를 기다린다.
- 작업량이 작을수록 측정지 대부분이 "꺼진 상태"에 도착한다(작게 약 86%: 하루 20장이 10시간에 흩어져 간격이 쿨다운 5분보다 길다). 이때 W2는 장마다 기동 지연을 낸다.
- 절대 금액은 크지 않다(W1 Fargate 24.12 USD/월 → W2 1.34~8.58 USD/월). [037](../037-measurement-sheet-unit-cost/README.md)의 장당 비용 월 7~217 USD와 비교해 우선순위를 정한다.
- InfraFit 규칙 후보(후보): "KEDA 최소 0 워커가 공유 노드 그룹에 있음" → 절감 0으로 보고. "전용 노드·Fargate에서 최소 1 상시 워커의 사용률이 낮음" → W3 일정 검토.

## 가정·제외·한계

- 노드 기동 120초, Fargate 기동 60초, 노드 축소 대기 10분, 처리 시간(중앙값 20초), 도착 분포, 워커 자원(0.5 vCPU·1 GiB), 공유 노드 그룹의 다른 워크로드 요청은 모두 가정이다. 노드 기동과 Fargate 기동은 실측하지 않았다.
- 파드 시작은 로컬 Minikube(노드 1개, 작은 이미지 `python:3.12-alpine`)에서 잰 값이다. 실제 워커 이미지는 더 커서 캐시 없음 시간이 길어질 수 있다. KEDA의 큐 감지는 실측하지 않고 폴링 간격으로 모형화했다.
- 워커는 최대 1개로 두었다(KEDA가 여러 개로 늘리는 경우 제외). EC2 Linux 초 단위 과금·최소 60초는 이번에 재확인하지 않은 가정이다.
- Fargate 요율은 [2026-11-15 사본](../../references/aws-price-list-apn2-2026-11-15.json), EKS 클러스터 요금은 W1·W2·W3 공통이라 뺐다.
