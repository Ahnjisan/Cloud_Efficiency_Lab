# 033 — 입력 토큰 정의 차이와 교차 확인

[실험 목차](../README.md) · [Bedrock 노트](../../studies/aws/bedrock/README.md) · [032 요청 비용 분해](../032-llm-request-cost-breakdown/README.md)

**재현 PASS. H1 기각, H2 지지.** "입력 토큰"이 출처마다 캐시 토큰을 포함하기도 하고 빼기도 한다. 정의를 잘못 잡고 비용을 추정하면 얼마나 틀리는지, 그리고 청구 사용량과 비교해 어느 정의인지 가려낼 수 있는지를 합성 호출 기록으로 계산했다.

## 확인한 정의 (2026-11-15)

| 출처 | 입력 토큰 필드 | 캐시 토큰 포함 여부 | 근거 |
|---|---|---|---|
| Bedrock Converse API 응답 `usage.inputTokens` | 캐시되지 않은 입력만 | **제외** (전체 = inputTokens + cacheReadInputTokens + cacheWriteInputTokens) | [Prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) |
| Bedrock Responses API(OpenAI 모델) `usage.input_tokens` | 전체 입력 | **포함** (`cached_tokens`, `cache_write_tokens`는 그 일부) | 같은 문서 |
| CloudWatch `AWS/Bedrock` `InputTokenCount` | "입력의 토큰 수" | **미확인** (캐시 읽기·쓰기는 별도 지표) | [Bedrock runtime metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html) |
| 청구(Price List 사용 유형) | 입력·캐시 읽기·캐시 쓰기 별도 | 별도 사용 유형 | [2026-11-15 사본](../../references/aws-price-list-apn2-2026-11-15.json) |

같은 이름의 필드가 API마다 반대 정의를 쓴다. CloudWatch 지표는 정의가 문서에 없다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 입력 토큰 정의를 잘못 잡으면 비용 추정이 얼마나 틀리는가? 지표가 어느 정의를 따르는지 청구 자료로 가려낼 수 있는가? |
| 가설 H1 | 캐시 토큰이 입력의 50% 이상이면, 잘못된 정의로 만든 추정(E1~E3)은 모두 30% 이상 틀린다. |
| 가설 H2 | 지표 합계를 청구 수량(입력 / 입력 + 캐시 읽기 + 캐시 쓰기)과 비교하는 검사는 캐시 토큰 비중이 2% 이상이면 정의를 가려낸다(허용 오차 1%). |
| 추정 방식 | E1: 캐시 제외 입력 × 입력 요율(캐시 지표 무시). E2: 캐시 포함 입력 전부 × 입력 요율. E3: 캐시 포함 입력 × 입력 요율 + 캐시 지표 × 캐시 요율(이중 계산). E4: 올바른 계산 |
| 데이터 | 합성. 시나리오 ① 에이전트 월 3,000요청, 요청당 호출 2~6회, 도구 결과·출력 크기 ±50% 무작위, 시드 33 |
| 캐시 방식 | 고정 앞부분(시스템·도구 2,000토큰 뒤에 체크포인트), 자동 캐싱(체크포인트가 입력 끝으로 이동) |
| 모델·요율 | Claude Haiku 5.5(최소 캐시 512토큰): 입력 0.10, 캐시 읽기 0.01, 캐시 쓰기 0.125, 출력 0.50 USD/100만 토큰 |
| 그 밖의 가정 | 모델이 정해지기 전에 거부된 요청 2% (ModelId 없이 발행) |

## 결과

| 캐시 방식 | 캐시 토큰 비중 | 실제 비용 | E1 (캐시 무시) | E2 (전부 입력 요율) | E3 (이중 계산) |
|---|---:|---:|---:|---:|---:|
| 고정 앞부분 | 50.4% | 5.0565 USD | −18.4% | +28.7% | +47.1% |
| 자동 캐싱 | 100% | 4.1090 USD | −56.6% | +58.4% | +115.0% |

**정의 검사 — 캐시 토큰 비중을 줄여 가며**

| 캐시 토큰 비중 | 실제가 "제외"일 때 판정 | 실제가 "포함"일 때 판정 |
|---:|---|---|
| 50.4% | 제외 | 포함 |
| 2.5% | 제외 | 포함 |
| 1.0% | 제외 | 포함 |
| 0.5% | 구별 불가 | 구별 불가 |

자동 캐싱(100%)에서는 캐시되지 않은 입력이 0이라 "제외" 정의의 지표 합계가 0이 되고, 검사는 "해당 없음"을 냈다. 이 경우 0이라는 사실 자체가 제외 정의의 증거다.

**Invocations 대사**: ModelId로 걸러 보면 모델이 정해지기 전에 거부된 요청(가정 2% → 60건)이 빠져 전체 계열보다 0.5% 적다. 스로틀링·입력 검증 거부는 어느 계열의 `Invocations`에도 들어가지 않는다.

- **H1 기각**: 고정 앞부분 방식(캐시 비중 50.4%)에서 E1(−18%)과 E2(+29%)는 30%에 못 미쳤다. 이중 계산(E3)만 47%였다. 자동 캐싱(100%)에서는 세 방식 모두 56% 이상 틀렸다. 오차는 캐시 비중뿐 아니라 **캐시 읽기·쓰기의 비율**(쓰기는 입력 요율보다 비싸고 읽기는 10분의 1)에 좌우된다.
- **H2 지지**: 허용 오차 1%에서 캐시 비중 1.0%까지 정의를 가려냈다. 0.5% 이하에서는 두 정의의 합계가 허용 오차 안에 들어 구별할 수 없었다.

## 해석

- LLM 비용 규칙은 토큰 출처마다 **정의를 명시한 어댑터**가 있어야 한다. Converse 응답의 `inputTokens`와 Responses 응답의 `input_tokens`를 같은 열에 넣으면 안 된다.
- CloudWatch `InputTokenCount`의 정의는 문서로 확인되지 않았다. InfraFit은 이 지표로 비용을 계산하기 전에 **청구 사용량(입력 사용 유형의 월 수량)과 합계를 비교**해 정의를 정하고, 캐시 비중이 1% 미만이라 구별되지 않으면 어느 정의로 계산해도 오차가 1% 이내이므로 그대로 쓴다. 비교할 청구 자료가 없으면 금액은 **판단 보류**로 둔다.
- 가장 위험한 실수는 E3(포함 정의 지표 + 캐시 지표 합산)이다. 캐시를 많이 쓸수록 두 배 가까이 과대 추정한다.

## 가정·제외·한계

- CloudWatch 지표의 실제 정의는 실제 호출 없이 확인할 수 없다. 이 실험은 정의를 가려내는 **검사 방법**을 검증했을 뿐 실제 정의를 확인하지 않았다(실제 LLM 호출은 승인 범위 밖).
- 청구 자료의 지연·정정, 리전 간 추론(교차 리전 프로필) 사용 유형 차이는 넣지 않았다.
- 거부 비율 2%는 가정값이다.
