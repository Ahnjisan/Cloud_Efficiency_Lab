# 035 — 캐시 축출 정책별 적중률 (로컬 Redis 실측)

[실험 목차](../README.md) · [ElastiCache 학습 노트](../../studies/aws/elasticache/README.md) · [누수 패턴 4 — 캐시 손익분기](../../studies/methods/cost-leak-patterns.md#4-캐시사전-계산-손익분기)

**로컬 실측 완료, 요약 재현 PASS. H1 지지, H2 기각, H3 지지.** 같은 메모리(maxmemory 10 MB)에서 `allkeys-lru`, `volatile-lru`, `volatile-ttl`의 적중률과 축출 수를 같은 작업 순서로 3회씩 측정했다. 적중률 차이를 시나리오 ② 챗봇 응답 캐시의 원본 호출 비용으로 바꿔 계산했다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 캐시 크기가 같을 때 축출 정책만 바꿔도 적중률, 따라서 원본 호출 비용이 달라지는가? |
| 가설 H1 | `allkeys-lru`의 평균 적중률이 세 정책 중 가장 높다. |
| 가설 H2 | `volatile-*` 정책은 TTL 없는 키가 메모리를 채우면 쓰기 오류(OOM)가 난다(실행당 1건 이상). |
| 가설 H3 | 같은 시드 3회 반복의 적중률 범위가 정책마다 0.01 이하다. |
| 환경 | Redis 7.4 컨테이너 1개(`redis:7.4-alpine`), 컨테이너 메모리 한도 64 MiB, maxmemory 10 MB, 저장(RDB·AOF) 끔, 127.0.0.1 포트만 열기 |
| 작업 | 키 6만 개, 값 512 B, Zipf(s = 1.0) 인기도, 요청 15만 건, 캐시 어사이드(GET → 없으면 SET). 키의 50%만 TTL(600~3,600초, 실행 중 만료 없음). 50건씩 파이프라인 |
| 반복 | 시드 35 고정, 정책마다 3회. 실행마다 `FLUSHALL`·`CONFIG RESETSTAT` |
| 정리 | 실험 뒤 컨테이너·이미지 삭제와 삭제 확인을 결과에 기록 |

maxmemory는 처음에 24 MB로 정했으나, 실행 전에 작업이 실제로 건드리는 고유 키(26,764개, 약 16 MB)를 계산해 보니 축출이 거의 생기지 않아 **실행 전에** 10 MB로 낮췄다. 가설은 실행 전에 별도 문서로 남기지 않았고, 스크립트를 쓸 때 정한 판정 기준을 이 표로 옮겼다.

**메모리 조건.** 계획은 "여유 메모리 4 GiB 미만이면 건너뜀"이었다. 시작 시점 여유 메모리는 **3.34 GiB**였으나 사용자 지시("부족해도 그냥 실행")에 따라 실행했다. 컨테이너 사용량은 최대 13.34 MiB / 64 MiB였다.

## 결과

| 정책 | 평균 적중률 | 3회 범위 | 후반 50% 적중률 | 평균 축출 수 | 축출 / SET | OOM 오류 |
|---|---:|---:|---:|---:|---:|---:|
| allkeys-lru | **0.7849** | 0.0005 | 0.8115 | 19,077 | 0.59 | 0 |
| volatile-lru | 0.7569 | 0.0008 | 0.7563 | 22,889 | 0.63 | 0 |
| volatile-ttl | 0.7198 | 0.0003 | 0.6911 | 28,210 | 0.67 | 0 |

**원본 호출 비용으로 환산**(요청 100만 건당, 원본 = Claude Haiku 4.5 입력 1,500·출력 400 토큰 1회 = 0.0035 USD, [2026-11-15 사본](../../references/aws-price-list-apn2-2026-11-15.json)):

| 정책 | 원본 호출 | 원본 비용 |
|---|---:|---:|
| allkeys-lru | 215,100 | 752.85 USD |
| volatile-lru | 243,100 | 850.85 USD |
| volatile-ttl | 280,200 | 980.70 USD |

- **H1 지지**: `allkeys-lru`가 가장 높았다. `volatile-ttl`보다 적중률이 6.5%p 높고, 실패(원본 호출)는 23% 적다.
- **H2 기각**: OOM 오류는 0건이었다. 새로 쓰는 키의 절반이 늘 TTL을 가지므로 축출할 TTL 키가 끊기지 않았다. 대신 TTL 없는 키가 메모리에 고정되고 **TTL 키만 반복해서 밀려나** 축출 수가 늘고(+20%, +48%) 적중률이 떨어졌다. OOM은 TTL 키 비율이 더 낮을 때 생길 수 있으며 이번 조건에서는 확인하지 못했다.
- **H3 지지**: 정책별 3회 범위는 최대 0.0008이었다. Redis의 근사 LRU(표본 추출)에서 오는 차이만 남았다.
- `volatile-ttl`은 후반 적중률이 전반보다 낮았다(0.69). 남은 TTL이 짧은 키부터 지우므로 인기도와 무관하게 인기 키가 밀려날 수 있다.

## 해석

- 캐시 크기를 키우기 전에 **축출 정책과 TTL 부여 방식**을 먼저 본다. 같은 메모리에서 정책만으로 원본 호출이 23% 달라졌다. 원본이 LLM 호출처럼 비싸면 요청 100만 건당 약 228 USD 차이다.
- 판단 자료: `evicted_keys`, `keyspace_hits/misses`, TTL 있는 키의 비율, 정책 설정. TTL을 일부 키에만 주는 앱에서 `volatile-*`를 쓰면 TTL 없는 키가 메모리를 점유한다.
- 이 결과는 Zipf 인기도·고정 크기 값·단일 클라이언트 조건이다. 실제 접근 패턴이 시간에 따라 바뀌거나(최근성 위주) 값 크기가 다양하면 순위가 바뀔 수 있다.

## 가정·제외·한계

- ElastiCache가 아니라 로컬 Redis 7.4다. 엔진 동작은 같지만 노드 오버헤드·네트워크 지연은 다르다.
- `allkeys-lfu`, `volatile-lfu`, `allkeys-random`은 범위 밖이다.
- 50건 파이프라인 안에서 같은 키가 두 번 나오면 두 번째도 실패로 센다(파이프라인 안에서는 아직 SET 전). 세 정책에 같게 작용한다.
- 원본 비용은 시나리오 ②의 챗봇 응답 1건을 원본으로 본 가정이다. DB 읽기처럼 싼 원본이면 차이는 무시할 만하다.
