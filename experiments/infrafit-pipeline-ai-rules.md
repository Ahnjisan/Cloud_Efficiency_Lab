# InfraFit 적용 메모 — IoT 파이프라인·생성형 AI·모델 학습 규칙 후보

[실험 목차](README.md) · [최종 연구 보고서](../FINAL-REPORT.md) · [InfraFit MVP](../infrafit/README.md)

실험 016~022(그리고 [확장 범위 026~036](#확장-범위-규칙-후보-026036))를 InfraFit의 판정 규칙으로 옮길 때 필요한 입력, 판정 조건, 기준값과 그 근거 수준을 정리한다. 이 중 R-IOT-1, R-FH-1, R-BR-1, R-BR-2는 [InfraFit](../infrafit/README.md#워크로드-규칙-실험-016022-기반-선택-옵션)의 `--workloads` 옵션으로 구현했다(합성 입력, [기준값](../infrafit/thresholds.json)). 나머지 다섯 규칙도 AWS 공식 API·지표의 필드 이름으로 입력 형식을 정해 [운영 규칙](../infrafit/README.md#운영-규칙-r-fh-2-r-ath-12-r-sm-1-r-cost-1)으로 구현했다. R-COST-1은 판정이 아니라 조사 대기열로 출력한다. 기존 MVP의 판정 이름(**변경 검토 후보·유지·판단 보류**)을 그대로 쓴다.

**근거 수준 표기**
- **실험 확인**: 이 저장소의 합성·계산 실험으로 재현한 값이다. 실제 계정에서 측정한 값은 아니다.
- **공식 자료**: AWS 요금 페이지, 개발자 가이드, Price List의 규칙과 요율이다(2026-11-13 확인).
- **임시값**: 판정을 돌리려고 정한 값이다. 실제 계정 데이터로 다시 정해야 한다.

모든 규칙의 공통 보류 조건은 기존 MVP와 같다. 청구 행이 자원과 연결되지 않거나, 같은 기간의 업무량·품질 근거가 없거나, 입력이 서로 충돌하면 보류한다. 아래 표에는 규칙별로 추가되는 조건만 적는다.

## R-IOT-1 · IoT 소형 메시지 묶음 후보 ([016](016-iot-message-batching/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | 토픽(또는 디바이스 그룹)별 월 계량 메시지 수(CUR 사용량 `APN2-Messages`), 같은 기간 발행 메시지 수, 평균·최대 페이로드 크기, 전송 주기, 토픽별 허용 지연(사람이 입력), 규칙 수 |
| 변경 검토 후보 | 평균 페이로드 ≤ 1 KB **이고** 토픽 허용 지연 ≥ `(N−1) × 주기`인 N(≥2)이 있으며, 묶음 후 크기가 5 KB 경계보다 충분히 작음(아래 여유값). 예상 절감은 016 산식으로 계산 |
| 유지 | 평균 페이로드가 이미 5 KB 단위를 대부분 채움(묶어도 계량이 거의 그대로), 또는 경보·제어 토픽 |
| 판단 보류 | 토픽별 허용 지연이 입력되지 않음, 페이로드 크기 분포를 모름, 계량 메시지 수와 발행 수의 비율로 크기를 역산할 수 없음 |
| 기준값과 근거 | 5 KB 계량 단위와 요율 — **공식 자료**. 200 B·20건 묶음에서 메시지·규칙·액션 비용 95% 감소, 4,000 B에서는 20% — **실험 확인**. 페이로드 1 KB 기준, 경계 여유 5%(묶음 크기 ≤ 4,750 B) — **임시값** |
| 실제 계정에서 다시 확인할 점 | 5 KB가 5,000 B인지 5,120 B인지(경계 25건×200 B+구분자에서 계량이 2배로 갈림). MQTT 헤더·토픽 이름이 계량 크기에 들어가는지. Basic Ingest 사용 여부 |

## R-FH-1 · Firehose 소형 레코드 후보 ([016](016-iot-message-batching/README.md)·[019](019-pipeline-unit-cost/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | 스트림별 `IncomingRecords`, `IncomingBytes`, 청구 수집 GB(`APN2-BilledBytes`) |
| 변경 검토 후보 | 청구 GB ÷ 실제 수집 GB ≥ 3 (평균 레코드가 5 KB보다 훨씬 작음) **이고** 상류(IoT 규칙·생산자)에서 레코드를 합칠 수 있음 |
| 유지 | 비율 < 1.5 |
| 판단 보류 | 1.5~3 사이, 또는 `no-rounding` 요율 행이 청구에 나타남(적용 조건 미확인) |
| 기준값과 근거 | 레코드당 5 KB 올림 — **공식 자료**. 200 B 레코드는 약 25배로 과금 — **실험 확인**(계산). 비율 3과 1.5 — **임시값** |
| 다시 확인할 점 | IoT 규칙의 Firehose 액션이 메시지를 레코드로 넘기는 방식(배치 옵션 포함), 실제 청구 행에서 쓰이는 사용 유형 |

## R-FH-2 · Firehose 버퍼·작은 파일 후보 ([017](017-firehose-buffer-small-files/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | 스트림 설정(버퍼 크기·시간, 동적 파티셔닝 키), 유입 바이트/초, 일별 S3 객체 수·평균 크기, 하류 소비자의 허용 신선도(사람이 입력) |
| 변경 검토 후보 | 버퍼 시간이 먼저 닫히는 스트림(유입 × 시간 < 크기)에서 평균 객체 < 1 MiB **이고** 허용 신선도 ≥ 제안 버퍼 시간 |
| 유지 | 버퍼 크기가 먼저 닫히는 스트림 — 시간을 늘려도 객체 수가 줄지 않음(017 작업량 B, H4) |
| 판단 보류 | 허용 신선도 미입력, 동적 파티션 수를 모름 |
| 기준값과 근거 | 버퍼 범위 1~128 MiB·0~900초, 먼저 도달한 조건에서 전달 — **공식 자료**. 60→900초에서 하루 조회 객체 수 15분의 1, PUT 비용 차이 월 0.18 USD, 레코드 평균 대기 30→450초 — **실험 확인**. 1 MiB 기준 — **임시값** |
| 다시 확인할 점 | Firehose가 힌트와 다르게 전달하는 빈도, 압축·Parquet 변환 후 실제 객체 크기, 작은 파일이 Athena 쿼리 지연에 주는 영향(미측정) |

## R-ATH-1 · 행 기반 원본 전체 스캔 후보 ([018](018-format-partition-scan/README.md)·[019](019-pipeline-unit-cost/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | Athena 쿼리 기록(쿼리 ID, 테이블, `DataScannedInBytes`, 실행 시각), 테이블 형식·파티션 키(Glue Data Catalog), 테이블 크기 |
| 변경 검토 후보 | 테이블이 CSV·JSON **이고** 쿼리당 평균 스캔이 테이블 크기의 50% 이상이며 쿼리당 스캔이 10 MB를 넘음 → Parquet 변환(Firehose 형식 변환 또는 CTAS) 검토 |
| 유지 | 쿼리당 스캔이 대부분 10 MB 미만(최소 과금으로 비용이 줄지 않음), 또는 월 쿼리 수가 적어 형식 변환 요금(0.022 USD/GB)이 더 큼 |
| 판단 보류 | 쿼리 기록이 없음, 대표 쿼리의 `WHERE` 열을 모름 |
| 기준값과 근거 | 스캔 요율·10 MB 최소 — **공식 자료**(S3 데이터의 10 MB 최소는 Glue 요금 페이지 문장 근거). CSV 대비 Parquet 읽은 바이트 91~99.99% 감소, 중심 쿼리량에서 Athena가 기준 비용 1위 — **실험 확인**(로컬 대리 측정·가정 쿼리량). 50% 기준 — **임시값** |
| 다시 확인할 점 | 대리 측정과 실제 `DataScannedInBytes`의 차이, 압축 CSV의 과금 바이트 기준 |

## R-ATH-2 · 작은 Parquet 파일 합치기 후보 ([018](018-format-partition-scan/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | 테이블의 파티션별 파일 수·평균 파일 크기, 한 달 단위 쿼리의 스캔량 |
| 변경 검토 후보 | 평균 Parquet 파일 < 1 MiB **이고** 넓은 기간 쿼리의 스캔량이 10 MB를 넘음 |

| 다시 확인할 점 | Firehose Parquet의 실제 행 그룹·압축 설정, 실제 Athena 쿼리 지연 |

## R-BR-1 · Bedrock 프롬프트 캐싱 미적용 후보 ([020](020-bedrock-token-caching/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | 호출별 로그: 모델 ID, 추론 프로필(Global/Geographic), `inputTokens`, `cacheReadInputTokens`, `cacheWriteInputTokens`, 출력 토큰, 요청 시각, 실행(세션) ID, 앞부분 해시(지시문·도구 스키마). 교차 확인: CloudWatch 런타임 지표의 모델별 입력·출력·캐시 토큰 합계(2026-11-15 추가, [Bedrock 노트 7절](../studies/aws/bedrock/README.md#7-사용량은-어디서-측정하는가-2026-11-15-추가)) |
| 변경 검토 후보 | 캐싱을 쓰지 않음 **이고** 같은 앞부분 해시가 실행당 2회 이상 반복되며 앞부분 ≥ 모델 최소 길이(Claude 5.5: 512) |
| 유지 | 앞부분이 최소 길이 미만, 또는 같은 앞부분 요청이 대부분 TTL보다 긴 간격으로 단발 호출 |
| 판단 보류 | 호출별 로그 없이 월 청구 합계만 있음, 앞부분 해시를 구할 수 없음 |
| 기준값과 근거 | 캐시 최소 길이·TTL·과금 구분 — **공식 자료**. 실행당 2회 이상이면 미스 0에서 항상 이득(최소 11.1%), 1회 호출·하루 10회에서는 5분 TTL이 8.6% 손해 — **실험 확인**. 손익분기 적중률 21.7%(Haiku 5.5)·20.8%(Sonnet 5.5) — **공식 요율로 계산** |

## R-BR-2 · Bedrock 캐싱 역효과 후보 ([020](020-bedrock-token-caching/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | R-BR-1과 같음 |
| 변경 검토 후보 | 캐싱 사용 중 **이고** 실제 적중률 = 읽기 ÷ (읽기 + 쓰기) < 손익분기 적중률(5분 TTL 약 21%, 1시간 TTL 약 52%) |
| 유지 | 적중률이 손익분기보다 높음 |
| 판단 보류 | 관측 기간이 짧아 캐시 쓰기 건수가 적음, Global 교차 리전으로 미스가 몰린 기간이 섞임 |
| 기준값과 근거 | 손익분기 적중률 — **공식 요율로 계산**. 미스 20%에서는 5분 TTL이 1시간보다 유리한 조합이 114개 — **실험 확인**. 최소 관측 캐시 쓰기 20건 — **임시값** |
| 다시 확인할 점 | 실제 미스율, Geographic·리전 내 요율(서울 Price List에서 미확인), 1시간 TTL 사용 조건 |

품질 조건: 에이전트 호출 수나 출력 길이를 줄이는 변경은 이 메모의 규칙 범위 밖이다. 같은 평가 세트에서 완료율·정확도를 비교할 수 없으면 항상 보류한다.

## R-SM-1 · GPU 노트북·엔드포인트 유휴 후보 ([022](022-gpu-training-idle-cost/README.md)) — **구현됨**

| 항목 | 내용 |
|---|---|
| 판정 입력 | 노트북 인스턴스 상태 기간, 커널 활동·GPU 사용률, 같은 기간 학습 작업 시간, 엔드포인트별 호출 수·인스턴스 시간, 스토리지 볼륨 크기 |
| 변경 검토 후보 | GPU 노트북의 (실제 학습 시간 ÷ 켜진 시간) < 10% **이고** 노트북 안에서 장시간 작업이 돌지 않음 → 학습 작업 분리·스케줄. 엔드포인트 호출이 낮고 지연 요구가 콜드 스타트를 허용 → 서버리스·배치 검토 |
| 유지 | 학습 비율이 근무 시간의 대부분(022 손익분기 월 164시간), 또는 엔드포인트 상시 대기가 요구사항 |
| 판단 보류 | 커널·GPU 활동 자료 없음, 인스턴스 유형 간 학습 속도 비교 없음(g4dn vs g5) |
| 기준값과 근거 | 인스턴스·스토리지 요율 — **공식 자료**. 학습 16시간에서 상시 GPU 노트북이 분리 운영의 19.4배, 잔존 스토리지 월 3.69~8.48 USD — **실험 확인**(계산). 학습 비율 10% — **임시값** |
| 다시 확인할 점 | 학습 작업의 과금 단위·시작 오버헤드, 노트북 중지 상태의 실제 과금 항목, 자동 중지 동작 |

## R-COST-1 · 일별 비용 급증 경보 ([021](021-daily-cost-spike-detection/README.md)) — **구현됨**

이 규칙은 자원 변경 후보가 아니라 **조사 대기열**을 만든다.

| 항목 | 내용 |
|---|---|
| 판정 입력 | 서비스(또는 사용 유형)별 일별 순비용, 청구 데이터 도착 시각 |
| 경보 | 우선 R2(28일 중앙값 + 3 × 1.4826 × MAD, 중앙값 대비 10% 이상, 경보일을 기준선에 유지). R3(4주 같은 요일 중앙값 × 1.75, 10% 이상, 경보일 제외)는 아래 상한이 정해진 뒤에만 쓴다 |
| 보류 | 서비스 사용 이력 28일 미만(R3는 같은 요일 3주 미만), 당일 청구가 아직 도착하지 않음 |
| 기준값과 근거 | 합성 평가에서 R2(유지) 급증 재현율 97.8%·오탐 30일당 0.040, R3(제외) 98.9%·0.025 — **실험 확인**(급증 +50% 이상인 합성 조건). Cost Explorer 데이터 최대 24시간 지연 — **공식 자료**. k·r 값과 10% 하한 — **임시값**(실제 계정 시계열로 다시 조정) |
| 주의 | 경보일을 기준선에서 빼는 설정은 정상적인 수준 이동 뒤 경보가 멈추지 않는다(021에서 R2 오탐 0.040→0.50). 연속 경보 일수 상한과 수준 이동 승인 절차가 정해지기 전에는 제외 설정을 쓰지 않는다. 점진 증가는 별도 추세 규칙으로 다룬다 |
| 다시 확인할 점 | 작은 급증(+10%~+30%)의 재현율, 월초 일괄 청구·할인 변경으로 생기는 오탐, 서비스 합계와 사용 유형별 시계열 중 어느 단위가 나은지 |
| 실제 계정 점검 | [023](023-real-cost-spike-check/README.md): 실제 청구 410일에서 오탐 27건(서비스별). 월 고정 요금의 2월 일수 효과(+10.7%)가 10% 하한을 넘었고, 월 첫날 세금은 중앙값 0이라 매달 경보가 됐다. 기준값은 조정하지 않고 보류. 중앙값 0 처리와 월 일수 보정이 필요하다 |
| 보완 (024) | [024](024-cost-spike-rule-fixes/README.md): 세금 분리, 최소 증가액 0.50 USD/일(임시값), 달력 보정을 기본값으로 채택. 실제 오탐 27→0건, 합성 급증 재현율 97.8% 유지. 작은 급증(+10~30%) 재현율은 21.5%로, 이 규칙의 범위 밖 |

## 확장 범위 규칙 후보 (026~036)

ADR-0005 확장 범위(설계 단계 비용 모델, 누수 패턴 규칙과 서비스 팩, LLM·에이전트 비용, 컨테이너 실행 방식, 실제 환경 연동)를 위해 실험 026~036에서 나온 후보다. **모두 미구현**이며 구현은 InfraFit 저장소의 일이다(ADR-0001). 패턴 번호는 [누수 패턴 방법 노트](../studies/methods/cost-leak-patterns.md)를 따른다. 근거 수준의 "공식 자료"는 2026-11-15 확인이고, 요율은 [2026-11-15 사본](../references/aws-price-list-apn2-2026-11-15.json)이다.

**구조 제안.** 패턴 규칙은 일반식과 판단 자료만 갖고, 서비스별 단위·최소치·중지 방식·요율 행 이름은 서비스 팩으로 분리한다. 원형은 [scenarios/service_pack.py](scenarios/service_pack.py)와 [036 model.py](036-architecture-cost-model/model.py)다. 금액은 "청구 예상"과 "요율 × 실사용량"을 함께 내고, 둘의 차이로 패턴 1·7을 표시한다.
