# 017 — Firehose 버퍼 설정과 작은 파일

[실험 목차](../README.md) · [최종 연구 보고서](../../FINAL-REPORT.md) · [Firehose 학습 노트](../../studies/aws/kinesis-firehose/README.md)

**시뮬레이션 재현 PASS. H1 부분 기각, H2·H3·H4 지지.** Firehose의 버퍼 크기·시간 설정에 따라 S3 객체 수, 평균 객체 크기, 레코드가 S3에 나타나기까지의 대기, S3 요청 비용이 어떻게 바뀌는지 시뮬레이션했다. S3 요청 요율은 [서울 Price List 사본](../../references/aws-price-list-apn2-2026-11-13.json)(AmazonS3 게시일 2026-11-09)을 읽는다. AWS 호출은 없다.

## 실행 전 결정

| 항목 | 내용 |
|---|---|
| 질문 | 버퍼 설정을 바꾸면 S3 객체 수·PUT 비용·이후 조회 요청 수와 데이터 신선도가 어떻게 바뀌는가? |
| 가설 H1 | 작업량 A(초당 약 2 KB)에서는 버퍼 크기가 아니라 **버퍼 시간이 항상 먼저** 도달한다. 크기 조건으로 닫힌 버퍼가 하나라도 있으면 기각한다. |
| 가설 H2 | 작업량 A에서 버퍼 시간 60초와 900초의 S3 PUT 비용 차이는 월 1 USD 미만이다. |
| 가설 H3 | 작업량 A에서 하루치를 읽는 쿼리의 객체 수는 60초 설정이 900초 설정의 15배다. |
| 가설 H4 | 작업량 B(초당 약 200 KB)에서는 기본 크기 5 MiB가 버퍼 시간보다 먼저 도달해, 버퍼 시간을 바꿔도 객체 수가 같다. |
| 기준선 | Firehose 기본값(5 MiB, 300초), 파티션 없음 |
| 바꿀 변수 | 버퍼 크기 {1, 5, 64, 128} MiB, 버퍼 시간 {60, 300, 900}초, 동적 파티션 수 {1, 10}, 작업량 A(센서 100대·10초·200 B)·B(센서 1,000대·1초·200 B) |
| 통제 조건 | 레코드 200 B(압축 전), 전달 스트림 1개, 하루를 시뮬레이션해 30배로 월 환산, 시간 해상도 1초 |
| 데이터 | 합성. 각 센서가 매초 확률 `1/주기`로 레코드 1건을 내는 베르누이 도착 |
| 시드·반복 | 시드 1·2·3으로 3회 반복하고 범위를 기록. 파티션 10개는 파티션 1개를 같은 시드로 시뮬레이션해 10배로 곱함 |

버퍼는 첫 레코드가 들어올 때 열리고, 누적 크기가 크기 힌트에 도달하거나 열린 뒤 버퍼 시간이 지나면 닫힌다고 모형화했다. AWS는 두 값을 "힌트"라고 설명하며 서비스가 다른 값을 쓸 수 있다. 하루가 끝날 때 남은 버퍼가 대기를 부풀리지 않도록 하루 뒤 1,000초 동안 도착을 이어 가고, 하루 안에 열린 버퍼만 집계했다(첫 실행에서 이 경계 효과를 발견해 수정함).

## 결과

### 작업량 A — 센서 100대, 10초, 200 B (초당 약 2,000 B)

| 크기 / 시간 | 월 객체 수 | 평균 객체 | 크기 조건 비율 | 레코드 평균 대기 | 최대 대기 | 월 PUT 비용 | 하루치 조회 GET 수 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 5 MiB / 60초 | 43,200 | 117 KiB | 0% | 30.5초 | 60초 | 0.194 USD | 1,440 |
| 5 MiB / 300초 (기본) | 8,640 | 586 KiB | 0% | 150.4초 | 300초 | 0.039 USD | 288 |
| 5 MiB / 900초 | 2,880 | 1,758 KiB | 0% | 450.3초 | 900초 | 0.013 USD | 96 |
| 1 MiB / 900초 | 4,950 | 1,025 KiB | **100%** | 261.8초 | 544초 | 0.022 USD | 165 |
| 5 MiB / 60초, 구역 파티션 10개 | 428,300 | 11.8 KiB | 0% | 30.7초 | 60초 | 1.927 USD | 14,270~14,280 |
| 5 MiB / 900초, 구역 파티션 10개 | 28,800 | 176 KiB | 0% | 450.1초 | 900초 | 0.130 USD | 960 |

64 MiB·128 MiB는 5 MiB와 결과가 같았다. 세 시드의 객체 수 범위 폭은 파티션 10개·60초에서만 10개(하루 14,270~14,280)였고 나머지는 0이었다.

- **H1 부분 기각**: 크기 5 MiB 이상에서는 모든 버퍼가 시간 조건으로 닫혔다. 그러나 **1 MiB / 900초에서는 모든 버퍼가 크기 조건으로 닫혔다**(1 MiB가 약 524초 만에 참). 가설을 "5 MiB 이상에서"로 한정해야 맞다.
- **H2 지지**: 60초와 900초의 PUT 비용 차이는 월 **0.18 USD**였다.
- **H3 지지**: 하루치 조회의 객체 수 비율은 정확히 **15.0배**(1,440 vs 96)였다. 하루치 조회 1회의 GET 비용은 0.0005 USD 대 0.00003 USD로 둘 다 작다.
- 구역 10개로 동적 파티셔닝하면 객체 수가 약 10배, 평균 객체 크기가 약 1/10이 된다. 동적 파티셔닝의 객체당 요금(0.0066 USD/1,000)을 더하면 60초 설정에서 월 약 2.83 USD, 900초에서 0.19 USD다.

### 작업량 B — 센서 1,000대, 1초, 200 B (초당 200,000 B)

| 크기 / 시간 | 월 객체 수 | 평균 객체 | 크기 조건 비율 | 최대 대기 |
|---|---:|---:|---:|---:|
| 5 MiB / 60·300·900초 | 96,000 | 5,273 KiB | 100% | 26초 |
| 64 MiB / 60초 | 43,200 | 11,719 KiB | 0% | 60초 |
| 128 MiB / 900초 | 3,870 | 131,250 KiB | 100% | 671초 |

- **H4 지지**: 5 MiB에서는 버퍼 시간과 무관하게 하루 3,200개였다. 이 작업량에서 객체 수를 줄이려면 버퍼 시간이 아니라 **버퍼 크기**를 바꿔야 한다.

## 해석

- 유입량이 작을 때 PUT 비용 자체는 작다. 버퍼 설정의 실질적인 영향은 **신선도와 조회 단계의 객체 수**다. 900초 버퍼는 레코드 평균 대기를 30초에서 450초로 늘리는 대신 조회할 객체를 1/15로 줄인다.
- "작은 파일" 판정에는 유입 속도(바이트/초), 버퍼 설정, 파티션 수가 모두 필요하다. 객체 수만 보고 버퍼 시간을 늘리라고 권하면, 크기 조건이 먼저 도달하는 스트림에서는 효과가 없다.
- 하류 소비자의 허용 지연이 정해지지 않으면 버퍼 확대를 후보로 올리지 않는다.

## 가정·제외·한계

- 압축 전 크기다. GZIP·Snappy 압축과 Parquet 변환 후의 객체 크기는 측정하지 않았다(Parquet 크기는 [018](../018-format-partition-scan/README.md)에서 측정).
- Firehose가 실제로 힌트와 다르게 전달하는 경우, 재시도·실패, 전달 지연(네트워크·S3 쓰기 시간)은 모형에 없다.
- 파티션 10개는 독립 시뮬레이션이 아니라 1개 결과를 10배 했다. 파티션별 유입이 고르지 않으면 객체 수가 달라진다.
- 수집 요금(레코드당 5 KB 올림)은 버퍼와 무관하므로 이 실험에서 제외하고 [019](../019-pipeline-unit-cost/README.md)에서 합산한다.
- 조회 단계의 영향은 GET 요청 수로만 표현했다. 파일 열기 오버헤드와 쿼리 지연은 측정하지 않았다.
