# 015 — Kubernetes 반복 부하와 Deployment 롤백

[실험 목차](../README.md) · [최종 연구 보고서](../../FINAL-REPORT.md)

**실측 및 정리 PASS · 품질 회복 재현 1/3.** 세 번의 기준·축소·복원 시퀀스와 총 아홉 구간을 완료했다. 전용 프로필과 Docker 자원 정리를 확인했고, 실행 전후 기존 컨테이너 86개의 ID·상태 목록이 같았다. 시작 여유는 2.95 GiB, 감시 명령 중 관측한 최저 여유는 2.18 GiB였다. [실측 기록](live-attempt-1.json) · [집계](result.json)

기존 컨테이너 비교는 당시 실행을 감싼 스크립트가 양쪽에서 `docker ps -a --no-trunc --format "{{.ID}} {{.State}}"`를 읽어 집합을 비교한 결과다. 당시 출력은 `Existing container ID/state comparison: True counts: 86 86`이었다. 당시 목록과 해시는 저장되지 않아 원본 로그에서 독립적으로 재검산할 수 없다. 이후 실행기는 정렬한 ID·상태 행의 전후 SHA-256, 건수, 일치 여부를 기록한다.

기존 프로필과 다른 Minikube 프로필·kubeconfig·네트워크에 단일 복제본 Deployment를 구성한다. 100m Requests와 128 MiB 메모리 한도를 고정하고 CPU Limits만 1,000m → 500m → 1,000m로 바꾼다. 후보 변경은 `kubectl set resources`, 복원은 `kubectl rollout undo`로 수행한다. `Recreate` 전략을 사용하고 각 구간에서 준비된 Pod 한 개의 UID와 cgroup quota를 기록한다. 복원은 실험 순서에 포함했다.

[기존 실행기의 반복 모드](../006-kubernetes-resource-efficiency/run_live.py) · [부하 스크립트](../013-peak-rollback/load.js) · [원본 집계 코드](analyze.py)

같은 부하를 25회/초 목표로 12초간 제공한다. 품질 통과 기준은 p99 ≤ 200ms, 전송 요청 오류율 ≤ 1%, 제공 부하 대비 성공률 ≥ 99%다. 전송 요청과 미시작 반복의 합이 300건 이상이어야 품질을 판정한다. 실행기의 PASS는 측정과 정리를 완료했다는 뜻이고, 회복 관측은 같은 반복의 품질 판정이 통과 → 위반 → 통과인 경우 별도 집계한다.

집계기는 각 구간의 전후 cgroup quota와 k6 측정값을 원본에서 다시 검증한다. PASS로 기록된 로그에서 요청한 반복이나 구간이 누락되면 집계 오류로 처리한다. `py -3 -B experiments/015-kubernetes-rollback/test_analyze.py`로 정상 로그의 회복 1/3과 잘못된 quota·음수 지연·2회차 축소 구간 누락의 거부를 확인할 수 있다.

| 반복 | p99 기준 → 축소 → 복원 | 성공 / 제공 기준 → 축소 → 복원 | 품질 기준 |
|---|---|---|---|
| 1 | 145.12 → 541.05 → 122.27ms | 295/300 → 109/300 → 297/300 | 위반 → 위반 → 통과 |
| 2 | 107.06 → 467.33 → 111.55ms | 300/301 → 121/301 → 299/301 | 통과 → 위반 → 통과 |
| 3 | 68.34 → 431.93 → 111.40ms | 300/300 → 129/301 → 296/300 | 통과 → 위반 → 위반 |

전송된 요청의 HTTP 오류율은 전 구간 0%였다. 복원 후 p99는 세 번 모두 기준 이내였지만, 제공 부하 대비 성공률까지 포함하면 1·2회만 복원 구간을 통과했다. 1회는 기준 구간부터 성공률이 99%에 미달해 회복 재현으로 집계하지 않았다. 3회는 복원 구간 성공률 98.67%로 통과하지 못했다. 복원 호출부터 첫 관측 창 완료까지 17.69~18.85초였으며, 롤아웃·준비 대기·부하 창을 포함한다. 최초 회복 시각은 측정하지 않았다. 실측 기록에서 사용자 경로만 치환했다.

저장소 루트에서 `py -3 -B experiments/006-kubernetes-resource-efficiency/run_live.py --low-memory --rollback-repetitions 3`으로 실행한다. 이번 실행은 시작 여유 2.65 GiB까지 허용하는 `--bounded-rollback-memory`를 추가했다. 노드는 1,800 MiB로 요청했고, 감시 명령의 호스트 중단 하한은 1.5 GiB였다. stdout은 시도별 새 파일로 저장한다. 저장 로그 집계는 `py -3 -B experiments/015-kubernetes-rollback/analyze.py <원본 JSON 경로>`로 실행한다.

단일 로컬 노드의 고정 순서 실험이다. 첫 반복과 같은 시간대에 호스트에서 Terraform 로컬 검증을 수행했으며, 구간별 영향을 분리하지 않았다. 다중 노드나 트래픽 무중단 롤아웃, 롤백 자동 발동, 복구 시간 목표, EC2·EBS 복구, 실제 청구 대사는 별도 검증 범위다.
